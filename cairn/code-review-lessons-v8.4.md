## 一、最重要的教训（Top 3）

### 1. 回测前视偏差是"静默杀手"——比崩溃更危险
审查发现两处前视偏差：财务数据用当期快照回放历史、因子 IC 用"过去收益"当"未来收益"。这些 bug **不崩溃、不报错、甚至看起来结果很好**，但让回测收益虚高、因子失效被掩盖，实盘完全无法复现。

**铁律**：
- 任何回测中使用的数据，在决策时点 T **必须只包含 T 时刻及之前已披露/可得的信息**（point-in-time）
- 财务数据按**实际披露日**对齐，非报告期截止日（年报≤4/30、半年报≤8/31、季报≤季度末+1月）
- 因子值（T 日）与目标收益（T→T+F 未来收益）**必须严格错开数据区间**，禁止用过去收益近似未来收益
- 无法保证 point-in-time 时 **fail-closed**：拒绝该依赖，而非"假设数据不变"

### 2. fail-open 熔断 = 宣称有保护，实际没保护
`alpha_hedge_engine.monitor_drawdown` 在回撤≥12% 时只打日志，**既不禁止新建多头、也不强制买入对冲**。这是最危险的模式——开发者以为有硬控制，实际是软日志。

**铁律**：
- 风控函数的返回决策**必须被调用方真正消费**（HALT→禁买/抛异常，FORCE_HEDGE→真下单），不能只记日志
- 风控失败时默认 **fail-closed**（禁止交易、拒绝返回假信号），绝不能 fail-open（放行）
- 两套引擎（机构流水线 vs 独立引擎）的熔断行为**必须一致**，避免"一条路径是硬控制、另一条是软日志"

### 3. 硬编码的真实凭证/过期合约是"定时炸弹"
`.env` 明文硬编码真实 DEEPSEEK API Key；`portfolio.yaml` 全部期货/期权合约用已过期的 2507 合约。这类问题不报错，但一旦被 git 提交或实盘调用就出事。

**铁律**：
- 凭证**永不硬编码**，走系统密钥管理/环境变量注入，`.env` 必须 gitignore
- 合约/资产代码必须有**到期日校验**，下单前拒绝过期标的
- fallback 数据要带时间戳，过时快照禁止用于决策

## 三、可复用最佳实践（项目已验证有效）

### 1. fail-closed 数据兜底（`alpha_hedge_engine.py`）
- 数据不可用时**返回 NaN / 抛异常拒绝决策**，而不是返回硬编码假信号
- broker/数据源为 None 时返回 0 或显式降级，绝不伪造价格
- 区分**可恢复异常**（重试）与**致命异常**（fail-closed）

### 2. 分级熔断（`kill_switch.py` / `drawdown_breaker.py`）
- 保证金熔断三级：L1=50% 警告 / L2=65% 减仓 / L3=75% 强平（kill_switch）
- 回撤分级：WATCH → REDUCE → FORCE_HEDGE → HALT（drawdown_breaker）
- 阈值**配置化**，符号约定统一（回撤为负、保守取最小值），`evaluate` 返回可消费的 `allow_new_buy` 标志

### 3. 影子账户缓冲（`.env` TRADING_ENV=shadow）
- 实盘前用影子账户（10% 资金）验证，Signal 必须过 Shadow 才放行
- `TRADING_ENV` 作为安全环境开关，防止误实盘

### 4. 错误签名对齐（`cli_helpers.py`）
- 降级 stub 的函数签名**必须与完整版对齐**（含新参数），避免 `got unexpected keyword argument` 导致的静默降级
- stub 返回类型也要与调用方契约一致（None vs str），保持降级行为可预测

## 四、审查方法论沉淀（open-code-review 经验）

### 有效审查顺序（按资金风险排序）
1. **先审交易执行/下单**（资金/股数/涨跌停/成本）——错一个直接亏钱
2. **再审风控/对冲/熔断**（fail-open 是最隐蔽的）
3. **再审回测/数据管道**（前视/幸存者偏差，静默失真）
4. **最后审基础层/CLI/配置**（崩溃/泄露/假成功）

### 高效审查技巧
- **用 graph 工具优先**（code-review-graph MCP）：`get_impact_radius_tool` 查改动爆炸半径、`get_affected_flows_tool` 查影响执行路径，比全文件读 token 高效
- **优先精确而非召回**：只报告确认的真实缺陷，误报比漏报更伤信任（项目已有此原则）
- **关键 bug 必须亲自读源码验证**（子代理输出可能截断/推断），特别是 CRITICAL 级别
- **静态工具（ruff/bandit/vulture）只能抓风格/已定义模式**，前视偏差、fail-open、幸存者偏差这类**逻辑 bug 必须靠人工语义审查**

### 报告结构化
- 按 CRITICAL/HIGH/MEDIUM/LOW 分级，每条含：文件路径+行号 + 问题 + 影响 + 修复建议
- 必须区分"模块本身质量好"与"调用链是软控制"（如 drawdown_breaker 质量好但调用方没消费决策）
- 承认已修复的好实践，避免重复整改（项目已有大量 M*/BUG-0x 修复记录）

## 五、修复执行落地（2026-08-05 完成）与深层发现

审查报告 25 项问题已全部修复并通过验证。修复过程本身暴露了几个**审查时未深挖、但实际修复时才发现的关键点**，这些是比 bug 本身更宝贵的经验。

### 5.1 修复中发现的前视偏差"隐藏形态"
审查报告的 C1 只指出"用当期快照"。实际修复 point-in-time 时才发现两个更深的结构性障碍：

**① 价格数据缺日期轴**：`factor_history_builder` 的 `price_data` 只有 `closes/volumes` 等数值，没有日期。没有日期就无法把"决策日 t"映射到"财务披露日"。修复必须贯穿三层：`real_data_loader` 内嵌 `dates` → `orchestrator.run` 转发 → `build_factor_history` 提取。**教训：回测数据管道在设计时就应自带时间轴，而非事后补。**

**② 财报披露日规则**：A股财务 point-in-time 必须用**最迟披露日**（Q1≤4/30、Q2≤8/31、Q3≤10/31、Q4≤次年4/30），且**绝不能把报告期当披露日**。例如 2026-04-01 时，2025Q4 年报（4/30 披露）与 2026Q1（4/30 披露）都不可用，只能用到 2025Q3——**很多人会误以为 2025Q4 已可用**（以为年报在季度末就出）。这是前视偏差最隐蔽的来源。

**③ 测试预期要符合真实 valid_dates 行为**：`build_factor_history` 的 `valid_dates` 恒为「最后 N 个交易日」而非「从第 60 天起」，导致"披露日前"的调用实际都落在披露日后。**测试断言若与引擎真实行为不符，会得到看似失败实则正确的误判**。精确的披露日前/后截断应交给 `_point_in_time_fundamentals` 单元测试，集成测试只做"不越界"合理性校验。

### 5.2 因子 IC 正确性依赖"数据形态"而非"公式"
`calc_ic` 用过去收益近似，本质是**单时点横截面因子值无法算真正的时序 IC**（缺未来收益）。审查报告 C2 只说了"用过去收益"这一表象，实际根因是 `FactorValue.values` 只有单时点横截面。

**教训**：修复 IC 不能只改公式（lookback→forward），而要解决数据形态——要么提供因子历史序列（`factor_history_builder` 已产出），要么用真实未来收益。当前修复用 `closes[-1]/closes[-1-fwd]-1` 作为未来收益，消除了"因子值(基于过去) vs 回看收益(同一过去)"的自相关，但**完整正确的多日时序 IC 仍需基于因子历史序列**（如 `gate1_validation.calc_ic_series` 的滚动窗口方案）。

### 5.3 合约月份码解析的"坑"（A股期货/期权）
修复合约到期校验时发现月份码格式的隐蔽性：
- **4 位月份段是 YYMM**（`IF2608` = 2026年08月），不是 YYYYMM——`int("2608")` 会误判为 2608 年
- **期权短码 3 位 YMM**（`CF609P15600` = 2026年09月）：`6` 是年份个位，但**仅凭 `6` 无法确定是 2026 还是 2016/2036**，必须结合 as_of 推断（取「个位匹配且不早于 as_of 的最近年份」）
- **子串污染**：`C2507` 会误匹配 `TC2507`/`SC2507`/`IC2507`，批量替换必须"先长后短"

**教训**：资产代码解析必须精确、带 as_of 上下文，且批量替换要防子串污染。这些坑无法靠"读代码"发现，必须**用真实合约代码逐类测试**（期货 YYMM、期权短码、带后缀 .CFFEX、不可解析的 ETF）。

### 5.4 复权口径：qfq vs hfq 的本质取舍
- **qfq（前复权）**：历史随「最新价」整体改写，**不可复现**；适合"当前时点看历史收益率"
- **hfq（后复权）**：历史固定、可复现，适合"跨时点收益计算"；与未复权实时价通过复权因子关联
- **未复权**：实盘成交基准（真实成交价）

**修复选择**：历史 K 线 `qfq→hfq`（可复现），实时行情统一 `adjust:"none"`。**关键原则：同一计算中绝不混用 qfq 历史与未复权实时**，二者在除权日口径不一致会导致换仓/止盈偏差。

### 5.5 成交模型：成本 + fill 量一致性
`daily_trade_executor` 成交修复揭示两个问题：
- **成本缺失**：`fill_price = ref_price` 直接成交，未含佣金/印花税/滑点 → 持仓成本低估
- **fill 量不一致**：WT 拆分部分成交时 `fill_amount < qty*ref_price`，但 `shares += qty` 仍按完整 qty → 持仓虚增

**教训**：交易记录必须「按实际成交金额/含滑点价推导实际成交股数」，保证 shares 与 fill_amount 一致，且成本必须计入 avg_cost。用 `total_cost = actual_amount + commission + transfer_fee` 作为成本基础。

### 5.6 空 handler 的"假成功"陷阱
统一入口的 21 个模式是 `_deprecated_mode_stub`，但 `main()` 无条件传 `success=True`——**用户以为功能执行了，实际是占位符**。空函数体（`run_model_training` 等）执行后返回 None 也被记为成功。

**教训**：废弃/未实现的功能必须**显式抛错或返回失败标记**，绝不能静默返回"成功"。stub 应抛 `NotImplementedError` 并给替代入口；`main()` 应识别 stub 返回的 `{'deprecated': True}` → 非 0 退出码。
