# 完成声明 ≠ 完成：三类状态失真与防复发（2026-08-29）

> 同一天同一模式命中 3 次：CTX-A「94 用例全绿」但代码门禁根本没跑；ROADMAP 门禁清单标 ✅ 但 GH+-1 只是 4 行摘要、且第 4 条口径与原文不符；08-29 当天写的排期表又把已完成的 GH+-1 列回待办。
> 本文提炼三类失真的判据与防复发机制，是 `docs/CODE_REVIEW_PROCESS.md` §4.2 DoD 与 `skills/AGENT_SKILLS_ADAPTER.md` §0 karpathy 原则 4 的上位总结。

## 1. 三类失真

| 类型 | 表现 | 2026-08-29 实例 | 判据（一句话） |
|---|---|---|---|
| **A. 验证维度缺失** | 单一验证通过就宣布完成 | CTX-A 核心实现 94 pytest 全绿 → 实为 `ruff` 21 项未修、`black` 6 文件未格式化 | 完成 = 语义正确 **且** 门禁通过 **且** 契约闭环，三者缺一不可 |
| **B. 验收清单模板化** | 清单从模板复制后状态未回查实物 | Wave 9-GH+ 门禁三条全 ✅，其中 GH+-2 尚未开始 | 每个 ✅ 必须能指到「具体文件 + 日期 + 复现命令」 |
| **C. 口径漂移** | 摘要/二手转述与权威原文不一致 | GH+-1 第 4 条记成「验证结果—跑门禁」，原文实为「目标驱动执行—定义成功标准+任务转可验证目标」 | 原则/规范类集成必须绑定**权威原文文件路径** |

## 2. 共同根因

**状态声明的事实源与实物分离**：三类失真的共同点是「有一个看起来权威的状态载体（pytest 输出 / 门禁清单 / 摘要文档），但它不指向实物」。

- A 类：pytest 是**语义**事实源，不代表**工程**（ruff/black）事实源。
- B 类：清单是**模板**事实源，不代表**执行**事实源。
- C 类：摘要是**转述**事实源，不代表**原文**事实源。

推论：**任何"标记完成"的动作，都必须回答"标记的依据是什么、依据能不能复现"**。

## 3. 防复发机制（4 条，可直接执行）

### 3.1 完成三连（治 A）

新模块/新文件落地，同一轮内必跑，缺一不宣布完成：

```
ruff check --fix <改动文件>     # 工程维度
black <改动文件>                # 格式维度（顺带兜底 W292 缺尾换行）
pytest <相关测试> -q            # 语义维度
```

- 批量新文件由工具生成时（无尾换行高发），`black` 必须跑 —— 08-29 的 12 处 W292 全源于此。
- 声明完成前再补门禁三件套：`ruff_incremental_gate.py` + `engineering_debt_gate.py` + `assert_data_validity.py`。

### 3.2 打勾三要素（治 B）

验收清单/ROADMAP 里每个 `[x]` 或 ✅ 必须同时可指认：

1. **文件**（改了哪个/生成了哪个）
2. **日期 + 实证值**（如 `daily_workflow 2159 行 @08-28`，不是"已完成"三个字）
3. **复现命令**（别人能跑出来同样的值）

不满足三点的，退回 `[ ]`。**模板里的预置 ✅ 一律视为未验证**，首次经过时必须逐条回查。

### 3.3 权威原文锚定（治 C）

凡「借思想不引代码」的第三方原则/规范集成：

- 文档中显式写明**权威原文路径**（如 `e:\各种PY程序\andrej-karpathy-skills\CLAUDE.md`），并注明"改以原文为准，勿以摘要为准"。
- 后续修订摘要时**对着原文改**，不复述上一版摘要，否则漂移逐级放大。

### 3.4 排期/验收双向核对（治 B 复发）

每次更新排期文档或验收清单时，做一次双向核对：

- **正向**：清单里标 ✅ 的，回查实物是否真存在（文件/命令输出）。
- **反向**：实物已完成但清单仍为 `[ ]` 的，补打勾（08-29 发现 4 例：daily_workflow 2159、R10 裸债清零、覆盖率 0.833、GH+-1）。

## 4.1 实例 D：Phase B 状态文档与权威状态源漂移（2026-08-29 补登）

- **命中类型**：C 类口径漂移 + B 类验收清单失真（同一文档内 B3 状态自述与运行时矛盾）。
- **实例**：`docs/升级路线优化与排期_20260829.md`（08-29 早生成）在状态总览表 / 关键路径 / 主线任务表三处把 B3 写成「观察期 0/3 天 / 启用评估 09-02~04」；但 `config/feature_flags.yaml` 运行时 + `phase_b_status.json` + `scripts/phase_b_progressive_enabler.py --check` 显示 **B3（USE_AUTO_RETRAIN）已于 08-27 经 B 顺序门禁（`_check_b_order_gate`）合法推进启用**（11:44 越级推进已于 08-26 回滚）。文档生成早于 ROADMAP 的 08-29 实测纠正，未同步。
- **新子模式（B/C 类的延伸）**：**排期/状态文档与 flag 注册表（权威状态源）漂移**——排期文档自己"宣告"某 flag/B 阶段状态，却未回链权威事实源（flag 注册表运行时值 + enabler `--check` 输出）。这是 B 类（清单未回查实物）在"系统状态"维度的投影。
- **易混淆点（另一处口径漂移）**：**「flag 已启用」≠「阶段内健康检查通过」**。B3 标志 08-27 已落盘 `true`，但当前 Stage 3 auto_retrain 的**阶段内稳定日仅 2/3**（未达 3/3）；所以"当前卡点"是 Stage 3 健康门禁 FAIL，不是"B3 未启用"。两者必须分开陈述。
- **可复用核查方法**：凡涉及 Phase B flag / 阶段启用状态的陈述，先读 `scripts/phase_b_progressive_enabler.py --check` 输出（或等价读 `phase_b_status.json` 的 stage / flags_enabled + flag 注册表当前值），以其为单一事实源；文档文字状态若与之冲突，**以 enabler 输出为准并同步文档**（08-29 已据此把升级排期文档 B3 段改为"✅ 已启用（实际 08-27）"）。
- **防复发落点**：§3.4 排期/验收双向核对，增补——**系统状态类字段（flag / B 阶段 / 门禁）必须以 enabler `--check` 或等价权威输出为事实源，禁止文档自述状态**；更新排期/ROADMAP 时，状态段先跑 `--check` 再落笔。

## 5. 一句话结论

**不要用"某个绿灯"代替"完成"** —— 绿灯只证明它被点亮的那一个维度。声明完成前，问一遍：语义过了么？门禁过了么？闭环过了么？清单里的 ✅ 能指到文件和日期么？
