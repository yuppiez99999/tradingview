## 0. 为什么是 v4：标准不缺，缺的是卡点

2026-08-29 实测（不是引用旧报告，是当场跑出来的）：

| 实测项 | 命令 | 结果 |
|---|---|---|
| 全量静态检查 | `ruff check .`（项目配置） | 1640 文件 **0 告警** ✅ |
| 剥离豁免后真实债 | `ruff check --isolated --select F,E9,B,SIM`（排除第三方） | 443 处（**绝大多数是有意豁免**，见 §7.2） |
| 债务等级 | `engineering_debt_gate.py` | **RED** — D11 shadow 6/7 天未达标，v8.7 BLOCK |
| 分项健康度 | 同上报报告 | T1–T18、D1–D10 **全 OK**（覆盖率 0.8330、超大文件 ≤2000 行、daily_workflow 已拆至 2159 行） |
| 工作区可审查性 | `git status --porcelain` | **1 个未提交变更**（v3 目标 ≤100，早已达成） |
| 开发活跃度 | `git log --since="30 days ago"` | **242 次提交** |
| 分支纪律 | `git branch --show-current` | 当前在 **`1`** 分支；`main`/`master` 并存 |

**三条诊断（这是 v4 存在的原因）：**

1. **标准已足够好，但没有强制力。** v3 的 Q1–Q7、DoD、分级模型都是对的，可它们写在文档里靠自觉。证据：债务门禁 8-29 判定 RED、建议"冻结新功能优先还债"，而近 30 天仍有 242 次提交在推进新功能。**门禁响了，没人停车。**
2. **四份标准并存 = 没有标准。** v1.0 / v2 / v3 / SOP 内容重叠且已分叉（v1.0 甚至有两个 §4.2）。人不知道以谁为准时，默认以"手边那份"为准。
3. **"完成"没有机检卡点。** 08-29 `cairn/completion-claim-vs-actual-state` 记录：94 个用例全绿就宣布完成，ruff/black 根本没跑。**绿灯只证明它被点亮的那一个维度。**

**v4 的设计转向**：不再新增审查条目，而是把已有标准**逐条绑定到一个可执行的命令和退出码**。标准写进文档只是"建议"，标准绑到命令才是"门禁"。

## 1. 六道卡点（G0–G5）

每道卡点三要素：**触发时机 · 执行命令 · 判定退出码**。任何一道不过，变更不得前进。

```
G0 分支纪律 ──► G1 提交前 ──► G2 提 PR 前 ──► G3 CI 门禁 ──► G4 人工审查 ──► G5 债务状态
   (开工)        (pre-commit)     (自查三维度)      (增量静态)      (分级清单)      (RED 熔断)
```

### G0 · 分支纪律（开工前）

| 项 | 规则 |
|---|---|
| 分支命名 | `feat/xxx` `fix/xxx` `refactor/xxx` `hotfix/xxx` 四选一 |
| 禁止 | 直接在 `main` 提交；`main`/`master` 并存（**待清理**：当前两个分支共存） |
| 存活期 | ≤ 5 天，超期必须拆分——长分支必然产生大 PR，大 PR 必然审查失效 |
| 判据 | 分支名匹配 `^(feat\|fix\|refactor\|hotfix)/.+$` |

> 🔴 **当前不符规**：工作区在名为 `1` 的分支上（据 `cairn/LOG.md` 08-29 条目，该分支系
> 全量同步 GitHub 时有意创建并用于 `git push origin 1`）。即便出于实际操作便利，
> 也不符合回溯锚点要求——分支名是回溯的唯一线索，实盘出事要定位"哪次变更引入的"时，
> `1` 提供不了任何语义信息。建议同步完成后归并回 `main` 并删除。

### G1 · 提交前（pre-commit，`githooks/pre-commit`）

```bash
git config core.hooksPath githooks    # 一次性设置，每个 clone 都要做
```

拦截项：硬编码路径 → 悬挂引用 → P0 文件 `print()` → P0 启动自检（`--skip-datasource`）→ NaN 污染守卫。

**跳过**（仅紧急）：`SKIP_P0_CHECK=1` / `SKIP_P0_PRINT=1`；`.md/.txt/.gitignore` 变更自动跳过。

### G2 · 提 PR 前（开发者自查，三维度缺一不可）

> 来源：08-29 CTX-A 教训。pytest 是**语义**维度，不代表**工程**维度。

```bash
ruff check --fix <改动文件>          # 工程维度
black <改动文件>                      # 格式维度（顺带兜底 W292 缺尾换行）
pytest <相关测试> -q                  # 语义维度
```

外加门禁三件套（改动任何 P0 文件时）：

```bash
python scripts/ruff_incremental_gate.py <改动文件>
python scripts/engineering_debt_gate.py
python scripts/assert_data_validity.py
```

### G3 · CI 门禁（`.github/workflows/`）

- `ci.yml` 的 `incremental-static` job：只扫本次 PR 改动的 `.py`
- `quality-gate.yml`：增量 ruff + T201 + 工作区变更数
- `ci_integrity_check.py`：**Q6 断言 CI 引用的所有 `scripts/*.py` 存在**（v3 R1 的防复发机制，已落地）

> Windows 编码坑：CI 与本地都需 `PYTHONUTF8=1`，否则 GBK 解码非 ASCII 路径崩溃。

### G4 · 人工审查（分级 + 清单）

见 §2 严重度模型、§3 量化专项清单、§4 审查者职责。

### G5 · 债务状态熔断（**v4 新增，本次实测的最大缺口**）

`engineering_debt_gate.py` 的退出码必须驱动**开发行为**，而不只是生成一个报告：

| 退出码 | 等级 | 强制行为 |
|:---:|---|---|
| 0 | GREEN | 正常开发 |
| 1 | YELLOW | 正常开发，但**每周必须至少还 1 项债务** |
| 2 | **RED** | **冻结所有 `feat/*` 与 `refactor/*` 开工**；仅允许 `fix/*`（还债）+ `hotfix/*`。RED 持续 >7 天须出专项复盘 |

> 🔴 **这就是当前状态**：债务门禁已判 RED（D11 shadow 6/7 天），而近 30 天 242 次提交仍在推进
> `feat(new-modules)`、`feat(execution-core)` 等新功能。**门禁输出了结论，但没有接上行为开关。**
> G5 是 v4 相对 v3 最实质的升级：把"建议还债"变成"新功能不予开工"。

**落地方式**：本条初期靠纪律执行（项目为单人/小团队，暂不引入审批流）；
后续可固化为 `scripts/debt_freeze_gate.py`，在 `githooks/pre-commit` 中检查新分支类型与当前债务等级。

## 2. 严重度模型（沿用 v3，无变更）

| 级别 | 含义 | 能否带过门禁 | 处理时效 |
|---|---|---|---|
| 🔴 **P0 阻断** | 资金安全 / 实盘正确性 / 数据正确性缺陷；门禁或 CI 配置失效；工作区未收敛 | 否（exit 1） | 立即 |
| 🟡 **P1 建议** | 静默数值污染、可观测性缺失、明显逻辑隐患、门禁健壮性 | 否（应拦） | 本周内 |
| 💭 **P2/P3** | 风格、可读性、非资金路径瑕疵、存量债务 | 是 | 周期清理 |

**资金安全升格规则**：任何触及「交易日期 / 行情数据 / 资金计算 / 风控阈值 / 下单指令」的缺陷，**一律升格 P0**——不论原始判级。

## 3. 量化系统专项清单（Q1–Q8）

> 这些规则静态工具抓不到，只会静默腐蚀决策。审查每一笔涉数据代码时逐条核对。

沿用 v3 的 Q1–Q7：

- **Q1 相关系数/IC 必须 `np.isfinite` 守卫** — `np.corrcoef`/`spearmanr` 对常数序列返回 NaN 且不报错。先判方差再算，非有限按 0。
- **Q2 除零路径必须守卫** — `a/b`、`np.divide`、任何 `mean/std/var` 分母，可为 0 时须 `if denom != 0` 或 `np.where(b != 0, a/b, 0)`。
- **Q3 分母类参数构造期校验 > 0** — 优化器风险厌恶/收缩强度/置信度，显式 `if x <= 0: raise ValueError`。
- **Q4 陈旧/缓存数据必须标记 stale 并降级质量分** — 兜底数据命中时 `quality_score` 不得满分，禁止当实时数据流通。
- **Q5 禁止裸 `except:`** — 裸/宽泛 except 会吞掉 `KeyboardInterrupt`/`SystemExit` 并掩盖真实错误。
- **Q6 门禁自完整性** — CI 引用的 `scripts/*.py` 必须存在且可执行（由 `ci_integrity_check.py` 机检）。
- **Q7 单一事实源** — 成交/持仓/fills 必须有唯一落盘真相源；禁止"只生成不执行"的订单。PR 描述须说明订单最终进入哪个执行器。

**v4 新增：**

- **Q8 AI 审查纪律（本次实测催生）** — AI/Agent 产出的审查结论与"完成声明"，必须满足：
  1. 每条缺陷须给出**文件 + 行号 + 复现命令**，不接受"存在安全隐患"这类无锚点结论；
  2. AI 声明"已修复"时，必须有**门禁脚本输出**佐证（`ruff`/`debt_gate`/`pytest` 的实际输出，非自述）；
  3. 禁止用旧报告/旧注释判断当前状态——**重跑命令验证**（08-29 教训：注释称 SimulatedBroker 实为内部算术记账）。

> **待补**：v3 §11 要求将 Q1–Q5 升格为 `tests/contract/` 行为契约测试，**至今 `tests/contract/` 目录不存在**。
> 这是 v3 落地清单里唯一确认未完成项（其余 R1–R3、quality-gate.yml、PR 模板、daily_workflow 拆分均已完成）。

## 4. 审查者职责与 SLA

| 变更触及 | 审查者 | 必须核对 |
|---|---|---|
| P0 交易路径 | 2 人（其中 1 人须熟悉交易逻辑） | 全部 🔴 项 + Q1–Q8 |
| P1 核心业务 | 1 人 | 全部 🔴 项 |
| P2/P3 | 1 人（可异步） | 🔴 项抽查 |
| 纯文档/注释 | 免审 | — |

**单人/小团队替代方案**：`AI 审查 + 本人隔日复审`。隔一天再看自己的代码，检出率明显提高——这是认知偏差消退，不是玄学。

**SLA**：审查响应 24h；修改后复审 12h；超时 P2/P3 可自动合并，**P0/P1 不可**。

**审查者三条义务（v4 新增，针对"LGTM 式审查"）：**
1. **不留无锚点意见** — "这里可能有问题"必须补上"什么问题、怎么复现"。
2. **区分"读不懂"和"有缺陷"** — 前者是文档问题，后者才是阻断理由，不要混为一谈。
3. **抓不到问题的检查项要删掉** — 见 §6 复盘。

## 5. PR 规范

### 5.1 体量

| 变更行数 | 处置 |
|---|---|
| ≤ 200 行 | ✅ 理想 |
| 200–400 行 | ⚠️ 可接受，须在描述中说明为何无法拆分 |
| > 400 行 | 🔴 要求拆分（纯格式化/重命名/文件移动除外） |

超过 400 行，审查者缺陷检出率断崖下跌，得到的往往只是"LGTM"。

### 5.2 描述四要素

1. **改了什么** — 一句话
2. **为什么改** — 关联问题/需求
3. **影响面** — 是否触及 P0 交易路径、是否改变策略行为
4. **怎么验证** — 测试方式、回测结果（**涉及策略逻辑变更必须附回测对比**）

补充：涉及订单生成的，须说明订单进入哪个执行器（Q7）。

### 5.3 完成定义（DoD，强制）

- [ ] **三维度全绿**：`ruff` + `black` + `pytest`（08-29 CTX-A 教训）
- [ ] 门禁三件套：无新增 FAIL/RED
- [ ] Q1–Q8 专项核对通过
- [ ] 修复类变更带**回归测试**（负向：构造触发条件 → 断言已修复；即"回滚必红、修复必绿"）
- [ ] 无新增硬编码路径/凭证/行情
- [ ] 资金/数据/风控路径的改动，新增契约测试
- [ ] 缺陷已入 Backlog 或 FIX 批次
- [ ] 若修复了新的 bug 模式，已更新 `cairn/code-review-lessons-v8.4.md`

## 6. 紧急通道（hotfix）

**触发**：盘中故障影响下单 / 风控失效 / 数据错误致信号异常。

**流程**：
1. `hotfix/xxx` 分支，可跳过非必要门禁（**保留 ruff `F` 类检查**）
2. 合并后 **24h 内**补齐：PR 描述、测试、事后复盘
3. 每个 hotfix 必须回答：**为什么常规流程没拦住它？** 答案转化为新检查项——这是流程自我进化的唯一途径

**滥用防护**：hotfix > 3 次/月，说明常规流程有系统性问题，须专项复盘。

## 7. 存量债务治理

### 7.1 童子军规则

碰到哪里顺手清理哪里：该文件 `print()` → `logger`；静默 `except` → 加 `logger.exception`；缺类型注解 → 补上。单次成本低，不需额外排期。

### 7.2 增量卡死机制

存量问题不阻塞任何人，但**新增一个都进不来**。这样债务有限且递减，而非一边治一边涨。

**关于 443 处"剥离豁免后"告警的说明**（避免误读）：

这 443 处**不是 443 个缺陷**。它们是被 `ruff.toml` 中 474 行配置**有意豁免**的项，主要三类：

| 豁免类型 | 典型规则 | 豁免理由 |
|---|---|---|
| fail-safe 设计 | `BLE001` 宽泛 except | 编排/风控/执行层异常必须降级不崩溃（§3 Q5 的例外：此处须有 `logger.exception` 而非静默） |
| 用户交互输出 | `T201` print | CLI/UI/自检入口的 `print` 是合理的 |
| 金融数学惯例 | `N806/N803` | `S`/`K`/`T`/`Δ` 大写变量名是行业惯例，非命名违规 |

**审查时不要试图清零 443**，那会破坏 fail-safe 设计。正确做法是：**新增代码过增量门禁，存量按童子军规则渐进**。

> ⚠️ 但豁免必须可解释。每新增一条 `per-file-ignores`，必须在 `ruff.toml` 内写明理由
> （现有配置已基本遵守，如第 99 行 `daily_workflow.py` 的 F401 豁免注明了"统一入口 re-export"）。
> **无注释的豁免视为违规**。

## 8. 度量与复盘

### 8.1 每周看板

```bash
python scripts/quality_snapshot.py
python scripts/engineering_debt_gate.py
```

跟踪五个量：

| 指标 | 期望方向 |
|---|---|
| 债务等级（GREEN/YELLOW/RED） | 维持 GREEN，RED 持续 >7 天须复盘 |
| 增量门禁拦截次数 | 有值才说明门禁在起作用；长期为 0 需排查门禁是否失效 |
| P0 区 `print()` 数 | 单调递减 |
| `v8.3/` `.exception()` 数 | 单调递增 |
| hotfix 次数 | > 3/月 须专项复盘 |

### 8.2 阶段复盘三问

1. 门禁指标是否达成？未达成的**真实阻碍**是什么？
2. 有没有绕过流程的情况？为什么绕？
3. **哪些检查项从没抓到过问题？——删掉。** 只增加成本不产生价值的检查项比没有检查项更糟，它制造虚假安全感。
