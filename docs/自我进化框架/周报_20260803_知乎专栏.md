## 二、为什么要做"自我进化框架"

先讲清楚目标。一个完整的量化自我进化系统,应该具备四个能力:

```
感知  →  决策  →  执行  →  记忆
 ↑                              ↓
 └──────────  反馈闭环  ────────┘
```

- **感知**:监控因子漂移、策略衰减、市场状态变化
- **决策**:评估策略健康度,决定是否退役/重训/生成新因子
- **执行**:自动重训模型、自动生成因子、自动 AB 测试
- **记忆**:把每一次决策和结果记下来,避免重复踩坑

我的系统里这四块代码其实早就有了(Phase 0-4 共 29 个任务,代码量不小),但问题是:**它们一直在 dry\_run 空数据上跑**。这就好比给一辆车装了全套自动驾驶传感器,但传感器接的是模拟信号 — 看起来在工作,实际上路就会出事。

这一周的核心工作,就是把这辆车的传感器接到真实路况上。

## 三、三条主线进展

### 主线 1:代码质量加固 — 1009 处宽泛异常清零

#### 问题在哪

Python 里最容易写、也最危险的一行代码是:

```python
except Exception:
    pass
```

它把所有异常都吞掉,包括你根本没想到的异常。在量化系统里,这意味着:**当真实下单路径出 bug 时,你不会收到任何报错,只会看到账户净值莫名其妙往下掉**。

全项目扫描下来,这种宽泛异常有 **1009 处**:

- `ai_decision/` 模块:29 处
- `utils/` 模块:849 处
- `ms_strategy/` 模块:131 处

#### 怎么修

不是简单的"全局替换",而是**按调用场景精细化**:

```python
# 修复前 — 吞掉一切
try:
    response = requests.post(url, json=payload)
    data = response.json()
except Exception:
    data = {}

# 修复后 — 精确捕获,保留降级
try:
    response = requests.post(url, json=payload, timeout=10)
    response.raise_for_status()
    data = response.json()
except (requests.ConnectionError, requests.Timeout) as e:
    logger.warning("行情源网络异常,使用降级数据: %s", e)
    data = {}
except json.JSONDecodeError as e:
    logger.error("行情源响应格式错误: %s", e)
    data = {}
# 未列举的异常快速失败,便于运维定位
```

关键原则:**已知降级路径保留(网络抖动、格式错误),未知异常快速失败**(不能再吞)。

#### 工具链沉淀

过程中开发了几个可复用工具:

- `scripts/_scan_except_remaining.py` — 通用目录异常残留扫描器
- `scripts/_fix_except_batch.py` — 批量替换器(保留原有 `# noqa` 注释)
- `scripts/_fix_import_fallback_except.py` — 智能识别 `try/import` 块并改为 `ImportError`

其中最后一个工具准确率只有 30% — 这恰好说明:**自动化能解决量的问题,但质的问题还得靠人工**。6 处导入降级模式是我手工逐行改的,因为 try 块里混入了 `sys.path.insert` 之类非纯 import 语句,正则识别不准。

### 主线 2:函数重构 — 规则配置表模式

#### 问题在哪

AST 扫描出生产模块有 **74 个超长函数(>80 行)**、**42 个高复杂度函数(圈复杂度>15)**、**59 个多参数函数(参数>5)**。

最典型的例子是 `ops_diagnoser._diagnose_from_health`,154 行,5 段几乎一模一样的代码:

```python
# 修复前 — 5 段重复模板
def _diagnose_from_health(self, health_report, now):
    causes = []
    # 检查指标 1
    val = sub_metrics.get("datasource_redundancy", 1.0)
    threshold = self.thresholds["datasource_redundancy_low"]
    if val < threshold:
        if val < 0.3:
            severity = SEVERITY_HIGH
        else:
            severity = SEVERITY_MEDIUM
        causes.append(RootCause(
            cause_id=f"ops-datasource_redundancy_low-{now}",
            layer=LAYER_OPS,
            category="datasource_redundancy_low",
            severity=severity,
            evidence={"datasource_redundancy": val, "threshold": threshold, ...},
            suggested_fix=FixSuggestion(
                action_type=ACTION_DATASOURCE_SWITCH,
                description=f"数据源冗余度偏低 ({val:.2f} < {threshold})",
                ...
            ),
            ...
        ))
    # 检查指标 2 — 同样的模板再来一遍
    # 检查指标 3 — 同样的模板再来一遍
    # 检查指标 4 — 同样的模板再来一遍
    # 检查指标 5 — 同样的模板再来一遍
    return causes
```

#### 怎么修

把"规则"和"执行"分离 — 规则放进配置表,执行用一个循环统一处理:

```python
# 修复后 — 规则配置表 + 循环
_OPS_HEALTH_RULES = [
    {
        "metric_key": "datasource_redundancy",
        "threshold_key": "datasource_redundancy_low",
        "category": "datasource_redundancy_low",
        "severity_hi_threshold": 0.3,
        "action_type": ACTION_DATASOURCE_SWITCH,
        "description_tpl": "数据源冗余度偏低 ({val:.2f} < {threshold})",
        # ...
    },
    # 其他 4 条规则...
]

def _diagnose_from_health(self, health_report, now):
    causes = []
    for rule in self._OPS_HEALTH_RULES:
        val = float(sub_metrics.get(rule["metric_key"], 1.0))
        threshold = self.thresholds[rule["threshold_key"]]
        if val >= threshold:
            continue
        # 统一的 RootCause 构造逻辑
        causes.append(RootCause(...))
    return causes
```

**效果**:154 行 → 49 行(**-68%**)。更重要的是,**以后新增一条诊断规则,只需要在配置表加一行,不用复制粘贴 30 行模板**。

同样的模式应用了 3 次:

| 函数                                              | 重构前   | 重构后  | 降幅       | 模式                  |
| ----------------------------------------------- | ----- | ---- | -------- | ------------------- |
| `ops_diagnoser._diagnose_from_health`           | 154 行 | 49 行 | **-68%** | 规则配置表               |
| `strategy_diagnoser._diagnose_from_health`      | 100 行 | 53 行 | **-47%** | 规则配置表(支持固定/条件两种严重度) |
| `execution_selector.choose_execution_algorithm` | 129 行 | 86 行 | **-33%** | 提取 helper 函数        |

#### 一个工程洞察

重构这类"看起来在跑"的代码,最大的风险是**改了行为**。所以我坚持一个原则:**零行为变更** — 输入输出完全一致,只是内部结构变化。验证方法是跑前后对比测试,所有输出 dict 字段值必须 bit-for-bit 相等。

这次 3 个函数全部通过零行为变更验证。这种重构可以做,但**不能在交易时间做** — 周末最安全。

### 主线 3:文档状态对齐 — 一个被忽视的坑

#### 发现的问题

这是这一周最"打脸"的发现。我有三份文档同时记录自我进化框架的进度:

1. `docs/自我进化框架/TASK_自我进化框架.md` — 任务清单
2. `cairn/self-evolution-framework.md` — 知识专题文档(真相来源)
3. `cairn/ROADMAP.md` — 路线图

按理说三份应该一致。实际上有 **7 处状态对不上**:

| 任务                     | TASK 标记 | 实际状态    | 证据                              |
| ---------------------- | ------- | ------- | ------------------------------- |
| T0.1 深度盘点              | ⬜ TODO  | ✅ 已完成   | GAP\_ANALYSIS 文档已存在             |
| T0.2 Feature Flag      | ⬜ TODO  | ✅ 已完成   | 5 个 Flag 已在 yaml                |
| T0.4 DriftMonitor      | ⬜ TODO  | 🔄 进行中  | drift\_alerts.jsonl 已产出         |
| T0.5 StrategyEvaluator | ⬜ TODO  | 🔄 进行中  | score\_reports 已产出              |
| T1.6 补全 Evaluator      | ⬜ TODO  | ✅ 已完成   | 字段完整,小样本容错正常                    |
| T4.2 期权定价内核            | ✅ 已完成   | 🔄 部分完成 | theta\_engine.py:206-207 仍用简化估算 |
| T4.7 fineng 验收         | ✅ 已完成   | ⬜ 未开始   | 验收报告不存在                         |

**根本原因**:代码改了,文档没同步。这是工程上最常见的债 — 不是不会写文档,而是**没有机制保证文档跟代码一起变**。

#### 怎么修

**先核实事实,再改文档**。我用 AST + 配置文件 + reports 输出做了三方交叉验证:

```python
# 核实 T0.4 — DriftMonitor 是否真的在跑
path = "reports/evolution/drift_alerts.jsonl"
print(os.path.exists(path))  # True → 在跑

# 核实 T1.6 — StrategyEvaluator 字段是否完整
with open("reports/evolution/score_reports/score_2026-08-02.json") as f:
    report = json.load(f)
# 检查关键字段
assert "public_score" in report
assert "private_score" in report
assert "reward_hacking_risk" in report
assert "recommendation" in report
# 全部存在 → T1.6 实际已完成
```

**关键决策点**:用户选择了"严格按 ✅ DONE 计数"口径 — 进行中的不算完成。修正后完成率从原来的"25/29=86%"变成真实的 **24/29=83%**(原 cairn 写错了,因为 T4.7 从已完成降级为未开始,DONE 数减 1)。

**数字下降不丢人,数字不准才丢人**。一个 83% 但准确的数字,远比 86% 但有水的数字有用。

#### 建立机制

光修这一次不够,得有机制防止再发生。我做了两件事:

1. **Cairn 知识体系**:把"知识专题文档 > LOG 历史"的仲裁规则写进 `AGENTS.md`,以后文档冲突有章可循
2. **Claude Code Hooks**:开发工作流自动化 — 每次代码修改后,Hook 自动校验 `cairn/LOG.md` 是否更新(信息性提示,不阻断)

## 四、最关键的一步:把传感器接到真实数据上

前面三条主线都是"加固",这一步是"激活"。

### 问题诊断

自我进化框架的感知层(DriftMonitor + StrategyEvaluator)之前一直在 dry\_run 上跑,产出的所有报告都是基于空数据。这意味着 **2026-08-13 观察期满时,我没有任何真实数据做决策依据**。

打个比方:你装了行车记录仪,但镜头盖没打开 — 录了 14 天黑屏,然后让你判断这辆车安不安全。

### 解决方案:W1.3a 真实数据接入

新增 `utils/alpha/shadow_real_data_feeder.py`(750 行),核心功能:

```
真实行情数据源 (TDX)
       ↓
MarketDataProvider.get_historical_data()
       ↓
按持仓权重加权: daily_return = Σ(weight × (close/prev_close - 1))
       ↓
写入 daily_returns.jsonl (增量, 原子替换)
       ↓
DriftMonitor + StrategyEvaluator 真正"看见"市场
```

#### 关键设计决策

**1. 三种权重来源自动降级**

```python
# 优先级:trade_plan → strategy_plan → positions.json
weights = (
    load_trade_plan_weights(date) or    # 执行计划(最准)
    load_strategy_plan_weights(date) or  # 策略计划(次准)
    load_positions_weights()             # 持仓快照(兜底)
)
```

**2. 三道安全护栏**

- 单日 |收益率| > 5% → 标记 `abnormal_return` warning(不阻断,但留痕)
- 数据源全失败 → 跳过该日(不写脏数据)
- 覆盖率 < 80% → 标记 `partial_coverage`(降级使用)

**3. dry\_run 严格隔离**

这个踩过坑 — 第一版 `dry_run` 内部调用了 `feed_single_date`,结果"预览"模式下数据被写进了真实文件。重构后 `dry_run` 完全独立实现,**绝不碰真实数据文件**。

#### 测试覆盖

77 个单元测试,100% 通过,覆盖率 **93.95%**(AST 精确计算,不是 coverage.py 的粗略估计)。

测试用例覆盖:

- 正常路径(单日/历史回填)
- 异常路径(数据源失败/权重文件缺失/JSON 格式错误)
- 边界条件(空持仓/单只股票/全部停牌)
- 并发安全(原子写入)

## 五、几个工程上的反思

### 1. 自动化扫描器的误报率极高

这一周用 AST 扫描器扫了好几轮,得到的数字和实际差距很大:

| 扫描项  | 扫描报告   | 实际问题      | 误报率       |
| ---- | ------ | --------- | --------- |
| 除零风险 | 1016 处 | 真实无守护 7 处 | **99.3%** |
| 静默异常 | 368 处  | 实际 0 处    | **100%**  |
| 宽泛异常 | 1335 处 | 真实 1009 处 | 24%       |

**教训**:扫描器只能解决"找"的问题,不能解决"判"的问题。AI 时代,扫描器 + 子代理人工核实才是靠谱组合 — 让机器做粗筛,让人(或 AI)做精核。

### 2. 文档和代码的同步是工程问题,不是态度问题

不是"我没好好写文档",而是**没有机制保证文档跟代码一起变**。这次建立了两个机制:

- `AGENTS.md` 里的仲裁规则(知识专题文档 > LOG 历史)
- Hook 自动校验(代码改了 LOG 没更新就提醒)

机制比态度可靠。

### 3. "零行为变更"重构是最安全的加固方式

重构生产代码最大的恐惧是"改出 bug"。这次 3 个函数重构全部零行为变更,核心方法:

- 先写测试覆盖原行为
- 重构后跑同样的测试,输出必须 bit-for-bit 一致
- 不在交易时间做,周末最安全

### 4. 完成率口径要统一

同一个项目,三份文档写三个不同的完成率(86%、25/29、24/29) — 这种事在小项目里没事,在大项目里会要命。这次明确统一为"严格按 ✅ DONE 计数",简单粗暴但不会错。

## 七、结语

这一周最大的收获不是"清了 1009 处异常"或"重构了 3 个函数",而是建立了一套**让系统能被信任**的机制:

- 代码可以被信任,因为宽泛异常清零了,bug 不会再被静默吞掉
- 文档可以被信任,因为完成率口径统一了,数字和实际一致
- 重构可以被信任,因为有零行为变更测试兜底
- 数据可以被信任,因为传感器接到了真实行情上

量化系统本质是一个**信任链** — 你信任数据,才能信任信号;你信任信号,才能信任决策;你信任决策,才能按下下单键。这一周的工作,就是把这条信任链上每一个环节的"看起来在跑"换成"真的在跑"。

下一周的 08-13 决策日,我会带着真实数据坐到决策桌前 — 而不是带着 14 天的 dry\_run 黑屏。
