# 当 PSI=8.48 是统计噪音：一次 Shadow 账户数据质量闭环的完整设计

> 量化交易里最危险的不是模型不行，而是你以为模型不行——基于失真数据做出的"客观"判断，往往比没有判断更致命。

## 一、一场 PSI=8.48 的"虚假漂移"

2026 年 8 月 2 日，自我进化框架的漂移监控系统弹出一条 critical 级告警：

```
severity: critical
PSI: 4.37
baseline_mean: 0.0055
current_mean: -0.0107
```

PSI（Population Stability Index）是工业界衡量两个分布差异的标准指标。按教科书阈值，PSI > 0.5 就该回滚模型，4.37 已经是"严重漂移"。

**第一反应**：模型坏了，得重训。

**但等一下**——baseline_mean 是 0.0055，三条基线数据全是 0.0055，完全相同。这不是真实收益分布，这是占位符。

排查发现，Shadow 账户的 `daily_returns.jsonl` 里 6 条记录，只有 1 条是真实市场数据（16.7%），其余 5 条是回测回填和修复值。3 条零收益是假的（占位符），2 条收益方向和幅度严重失真——回测虚高 5 倍、虚低 12 倍。

于是我们清洗数据，只保留真实记录，重算 PSI。

结果：**PSI = 8.48**，比污染数据还高。

清洗后反而更"坏"了？这不是 bug，这是统计学陷阱。

## 二、两层数据失真

### 第一层：回测回填污染

Shadow 账户在观察期需要每日记录组合收益。但某些日期的真实行情馈送失败（数据源故障、路径错误、格式不匹配），系统用回测回填数据"补位"。

问题在于，回测回填数据和真实市场数据有本质区别：

| 数据类型 | 来源 | 特征 | 问题 |
|---------|------|------|------|
| 真实市场 | TDX/AKShare 实时收盘价 | 有随机波动 | 无 |
| 回测回填 | V9 模型历史回测 | 倾向平滑、方向稳定 | 虚高 5 倍 / 虚低 12 倍 |
| 占位符 | 系统默认值 | 0.0 或固定值 | 完全失真 |

6 条记录里 5 条是回测回填，基线 `[0.0055, 0.0055, 0.0055]` 就是 3 个重复的回测值。PSI=4.37 不是模型漂移，是数据污染。

### 第二层：小样本 PSI 陷阱

清洗后只剩 6 条真实数据。PSI 计算需要分桶（binning），6 个样本分 10 个桶，多数桶是 0 或 1。

PSI 公式：

```
PSI = Σ (actual_i% - expected_i%) × ln(actual_i% / expected_i%)
```

当桶里只有 0 或 1 个样本时，`ln(actual/expected)` 在边界值处剧烈波动。一个异常值就能让 PSI 从 0.5 跳到 5+。

**实测对比**：
- 污染数据（3+3 样本）：PSI = 4.37 → critical
- 清洗后真实数据（3+3 样本）：PSI = 8.48 → critical（更高，因为真实数据方差更大）
- **两者都是统计噪音，非真实漂移**

工业级 PSI 阈值（0.1 / 0.25 / 0.5）假设样本量 ≥ 20。6 天样本的 PSI 没有统计意义。

## 三、数据质量闭环设计

### 3.1 设计目标

| 目标 | 解决方案 |
|------|---------|
| 剔除回测回填污染 | 数据清洗脚本标记 4 类质量，漂移判定仅用 real |
| 拦截小样本 PSI 误判 | 14 天双重门槛看门狗，未达标不触发 |
| 告警可溯源 | 告警条目嵌入 data_quality 计数 + cleaned_file_hash |
| 幂等不堆积 | 同日重复运行替换当日告警 |
| 断档可感知 | 连续 ≥2 交易日无新数据则告警 |

### 3.2 三脚本协同

```
┌─────────────────────────────────────────────────────────────┐
│  ① clean_shadow_returns.py  (数据清洗)                       │
│  输入: daily_returns.jsonl (原始, 可能含污染)                 │
│  输出: daily_returns_cleaned.jsonl  (带 quality 标签)        │
│  动作: 标记 real/backtest/fixed/missing + 检测缺失交易日       │
└──────────────────────────┬──────────────────────────────────┘
                           │ (清洗后数据)
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  ② integrate_cleaned_to_drift.py  (漂移告警集成)              │
│  输入: daily_returns_cleaned.jsonl                           │
│  输出: drift_alerts.jsonl  (漂移告警, 幂等替换)                │
│  动作: 过滤 real → 切分基线/当前 → compute_prediction_drift   │
└──────────────────────────┬──────────────────────────────────┘
                           │ (被看门狗条件触发)
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  ③ observation_watchdog.py  (达标看门狗)                      │
│  输入: observation_progress.json + daily_returns_cleaned.jsonl│
│  输出: observation_watchdog.jsonl  (监控日志)                 │
│  动作: 双重门槛判定 → 达标触发 / 未达标跳过 → 断档检测         │
└─────────────────────────────────────────────────────────────┘
```

数据单向流动：原始文件 → 清洗文件 → 告警/进度，绝不反向写入。质量标签从清洗脚本产出后，一路透传到告警条目的 `data_quality` 字段。

### 3.3 数据质量分类标准

清洗脚本按优先级 `real > fixed > backtest > unknown` 分类：

| 标签 | 判定条件 | 含义 | 漂移判定是否使用 |
|------|---------|------|-----------------|
| real | source 含 real_market 或 w13a | 真实市场馈送 | ✅ 使用 |
| fixed | source 含 fixed | 人工/脚本修复值 | ❌ 剔除 |
| backtest | source 含 backtest | 回测回填 | ❌ 剔除 |
| missing | 检测出的缺失交易日 | 断档占位 | ❌ 剔除 |

### 3.4 两层门槛：从低到高逐级拦截

这是整个闭环最核心的设计。两个门槛，位置不同，作用不同：

| 层级 | 门槛 | 位置 | 作用 |
|------|------|------|------|
| 集成器层 | MIN_REAL_SAMPLES_FOR_DRIFT = 5 | integrate_cleaned_to_drift.py | 最低可运行门槛，<5 条返回 skipped |
| 看门狗层 | DEFAULT_REQUIRED_DAYS = 14 | observation_watchdog.py | 统计可信门槛，<14 天不触发 |

**为什么需要两层？**

- **正常流程**：看门狗（14 天）先检查，通过才调用集成器，集成器的 5 天门槛不会触发
- **强制触发**（`--force-trigger`）：跳过看门狗 14 天门槛，直接调用集成器，此时 5 天门槛作为兜底
- **极端情况**：即使强制触发，<5 条真实数据仍返回 skipped，不会产生无意义告警

14 天门槛的依据：观察期最小周期（硬约束）+ PSI 统计稳定性（经验上 ≥20 样本才稳定，14 天可切分为 8+6，勉强达到 PSI 可信下限）。

**注意**：14 天是"最低门槛"而非"充分门槛"。即使达标，PSI 仍需结合 KS 统计量、均值差异、业务上下文综合判断。

### 3.5 双重门槛（GATE-A + GATE-B）

看门狗在触发漂移判定前执行双重门槛检查，任一不满足则跳过：

| 门槛 | 条件 | 防范的失效模式 |
|------|------|---------------|
| GATE-A | days_completed >= 14 | 日历时间不足（观察期未满 14 天，PSI 统计失真） |
| GATE-B | real_records >= 14 | 真实数据不足（天数达标但数据断档/质量差） |

**为什么需要双门槛？** GATE-A 的 `days_completed` 来自 `observation_tracker.py`，统计的是 `daily_returns.jsonl` 的去重日期数（含所有质量类型，不限于 real）。如果写入的是 backtest/fixed 数据，GATE-A 仍可能通过——这时由 GATE-B 拦截。GATE-B 直接数清洗文件里的 real 记录数，是更严格的真实数据量检查。

## 四、Day 7 实战验证

2026 年 8 月 4 日，观察期第 7 天，首次端到端验证三步命令。

### 4.1 三步命令

```bash
# 第一步：回填今日真实数据（从 TDX/AKShare 拉收盘价计算组合收益）
python scripts/backfill_shadow_history.py --start-date 2026-08-04 --end-date 2026-08-04

# 第二步：清洗数据（标记质量，写入 daily_returns_cleaned.jsonl）
python scripts/clean_shadow_returns.py

# 第三步：运行看门狗（检查门槛 + 刷新进度 + 达标则触发漂移判定）
python scripts/observation_watchdog.py
```

### 4.2 执行结果

| 步骤 | 结果 |
|------|------|
| ① 回填 | 26 标的 100% 覆盖，日收益 -0.0603%，写入 daily_returns.jsonl |
| ② 清洗 | 7 条记录全部 quality=real，写入 daily_returns_cleaned.jsonl |
| ③ 看门狗 | GATE-A 6/14 FAIL + GATE-B 7/14 FAIL，正确拦截，断档恢复 0 天 |

看门狗输出：

**正确拦截。** 没有基于 7 天样本产出无意义的 PSI 告警。

### 4.3 实战经验

1. **盘后 15:00 收盘后执行**：数据源（TDX/AKShare）才能拿到收盘价，盘中运行拿到的是最新价而非收盘价
2. **三步命令必须顺序执行**：回填 → 清洗 → 看门狗，不可并行（看门狗依赖清洗后的文件）
3. **`--dry-run` 预检**：正式回填前先 dry-run 探查数据源是否有今日数据，避免空跑

## 五、一个意料之外的踩坑：GATE-A 与 GATE-B 不一致

执行完三步命令后，看门狗报告出现了一个有意思的现象：

```
GATE-A (天数 >= 14):     ✗ FAIL  (6 天)    ← 来自 observation_progress.json
GATE-B (真实数据 >= 14): ✗ FAIL  (7 条)    ← 来自 daily_returns_cleaned.jsonl
```

GATE-A 显示 6 天，GATE-B 显示 7 条。明明是同一天的数据，为什么不一致？

**根因**：两个门槛读取的数据源不同。

- GATE-A 读取 `observation_progress.json` 的 `days_completed`，这个字段由 `observation_tracker.generate_snapshot()` 更新，是定时任务（v84_PostMarket）刷新的
- GATE-B 直接统计 `daily_returns_cleaned.jsonl` 的 real 记录数，是实时更新的

三步命令的流程是：backfill 写入原始文件 → clean 刷新清洗文件 → watchdog 读取进度文件。但进度文件的 `days_completed` 尚未被 `observation_tracker` 刷新（定时任务还没到），导致 GATE-A 滞后于 GATE-B。

**影响**：不影响核心逻辑。两层门槛都 FAIL 时正确拦截，都 PASS 时正确触发。仅在天数临界（如恰好 14 天）时可能出现 GATE-A 滞后导致延迟一天触发，可接受。

**应对**：无需修复。`days_completed` 会在下次 `observation_tracker` 运行时自动刷新。若需立即同步，可手动运行 `observation_tracker.py`。

这个踩坑的价值在于：**双数据源设计必须考虑刷新时机的不一致性**。如果 GATE-A 和 GATE-B 都读同一个文件，就不会有这个问题——但也就失去了双门槛交叉验证的意义。

## 六、漂移响应链路调研：代码已完整，但从未真实跑过

观察期数据收集正常推进后，自然会问：**14 天达标后，漂移触发了的响应链路准备好了吗？**

调研发现，漂移响应的代码已经完整实现：

```
漂移检测链路 (已就绪 ✅):
  cleaned.jsonl → observation_watchdog → integrate_cleaned_to_drift
  → compute_prediction_drift → drift_alerts.jsonl

漂移响应链路 (代码已存在, Feature Flag 默认关闭 ⏸):
  drift_alerts.jsonl → DriftMonitor._check_retrain_trigger
  → AutoRetrainScheduler.trigger_retrain (DRIFT_DETECTED)
  → V9 训练脚本 (subprocess 隔离) → ModelRegistry 注册
  → ABTestFramework (champion vs challenger) → promote_challenger / rollback
```

| 模块 | 状态 | 说明 |
|------|------|------|
| AutoRetrainScheduler | ✅ 已实现 | DRIFT_DETECTED 触发 + V9 训练 + 注册 |
| MLOpsPipeline | ✅ 已实现 | Facade 整合 model_registry + ab_testing + drift_monitor |
| ABTestFramework | ✅ 已实现 | champion vs challenger + promote_challenger |
| Phase 3 全链路测试 | ✅ 已通过 | 模拟漂移 → 检测 → 重训 → A/B → 晋升 |

**但有一个缺口**：Phase 3 测试里 DriftMonitor 和 AutoRetrainScheduler 都是 mock 的。整条链路从未用真实 Shadow 数据端到端跑过。

这意味着：代码写好了，单元测试过了，但"真枪实弹"的集成验证还没做。

## 七、一个"不提前模拟"的决策

发现缺口后，有两个选择：

**选项 A：提前模拟漂移注入**。构造高 PSI 数据，驱动真实（非 mock）的 retrain + 回测链路，提前暴露 Wave 2 启用时的集成问题。

**选项 B：等 08-14 自然触发**。尊重观察期设计，14 天达标后用真实 PSI/KS 触发漂移判定，拿到真实数据而非构造数据。

我们选择了 B。

**为什么不提前模拟？**

1. **尊重观察期设计的原始意图**。观察期存在的意义就是积累真实数据，用构造数据提前触发违背了这个设计。模拟数据再逼真，也不是真实市场。

2. **真实 PSI/KS 比构造数据更有价值**。14 天后自然触发的 PSI 是真实分布差异，构造的 PSI 是人为设定的。用真实数据验证链路，一次顶十次模拟。

3. **Feature Flag 闸门保护**。Wave 2 B3（08-26→29）才会启用 `USE_AUTO_RETRAIN`，在此之前所有漂移告警只是记录，不会触发重训。即使 08-14 触发了漂移判定，EvolutionOrchestrator 在观察期内也强制 `evaluate_only`，不会自动执行任何操作。

4. **降低复杂性**。模拟漂移注入需要构造数据、mock 部分链路、验证断言——引入新的测试代码本身就有维护成本。等自然触发是"零代码"验证。

**代价**：如果链路有集成 bug，要到 08-14 才发现，修复时间窗口更紧。但考虑到 Feature Flag 保护（08-26 才真正启用 auto_retrain），中间有 12 天缓冲，足够修复。

这个决策的核心原则是：**能用真实数据验证的，不用模拟数据**。量化交易系统里，真实数据的价值永远高于构造数据。

## 八、幂等告警：一个被忽略的工程细节

在设计闭环时，还发现了一个旧机制的工程缺陷。

**旧机制**（`daily_evolution_check.py`）：每次运行都追加一行到 `drift_alerts.jsonl`。同日多次运行会堆积重复告警。

**问题**：下游消费者（EvolutionOrchestrator）假设每条告警是独立事件。如果同一天产出 3 条 critical 告警，EvolutionOrchestrator 会做 3 次决策——但其实是同一个漂移事件。

**新机制**（`integrate_cleaned_to_drift.py`）：写入前先扫描文件，用 timestamp 的日期部分（YYYY-MM-DD）匹配当日已有告警，替换而非追加。

```python
# 幂等写入逻辑
today_str = datetime.now(timezone.utc).strftime("%Y-%m-%d")
existing_lines = []
for line in read(drift_alerts_file):
    rec = json.loads(line)
    if str(rec.get("timestamp", ""))[:10] == today_str:
        continue  # 跳过旧告警
    existing_lines.append(line)
write(drift_alerts_file, existing_lines + [new_alert])
```

**设计权衡**：选择"同日替换"而非"同日跳过"。因为重跑时可能用了更新的清洗数据（如当日补录了断档），需要让新告警覆盖旧告警。

**教训**：告警写入必须幂等。幂等设计应基于业务时间（日期）而非物理时间（时间戳）。下游消费者不应承担去重责任。

## 九、总结：三个核心经验

### 经验一：回测回填数据不能替代真实市场数据

3 天零收益全是假的，2 天收益方向/幅度严重失真（虚高 5 倍 / 虚低 12 倍）。观察期必须用真实数据才能做有意义的决策。

**推论**：任何数据管道的"补位"机制都有污染风险。回测回填、均值填充、前向填充——这些技术在回测里可以接受，但在实盘观察期里是毒药。实盘观察期的数据缺失，宁可断档告警，不可静默补位。

### 经验二：PSI 在小样本下不可靠

6 天样本的 PSI=8.48 是统计噪音，不是真实漂移。工业级 PSI 阈值假设样本量 ≥ 20，14 天门槛是观察期硬约束与 PSI 统计稳定性的折中。

**推论**：任何基于小样本的统计指标都应视为不可靠。PSI 如此，IC 如此，Sharpe 如此。做决策前先问：样本量够吗？

### 经验三：能用真实数据验证的，不用模拟数据

漂移响应链路代码已完整但从未真实跑过。我们没有提前模拟注入，而是等 08-14 自然触发。真实 PSI/KS 比构造数据更有价值，Feature Flag 闸门提供了足够的安全缓冲。

**推论**：测试用 mock 是必要的（快速反馈），但集成验证要用真实数据。mock 验证的是"代码逻辑正确"，真实数据验证的是"系统在真实条件下工作"。两者不可替代。
