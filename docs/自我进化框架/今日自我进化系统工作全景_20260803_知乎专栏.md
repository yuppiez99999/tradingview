## 二、主线 1:GNN 因子 — 从 +0.039 证伪到真信号入库(摘要)

这是今天最大的一条线,从早到晚贯穿全天。完整过程我已经写在专题文章里,这里只做一句话摘要:

> **发现 5 个 Bug(3 P0 前视偏差 + GAT 掩码泄漏,2 P1 Gate 判定 + 夏普定义)→ 修复后重测 → 亲手证伪自己此前记录的 +0.039 GAT 增益结论(实际 +0.0017,差距 23 倍)→ 按 Gate2 FAIL 回退 Layer 2 → 把 Layer 1 的 CHAIN_MOM_60D 推进 S5 组合层面检验 PASS(边际夏普改善 +1.7948 >> 阈值 0.05)**。

几个值得单独点出的工程洞察:

1. **前视偏差不会让代码报错,只会让结果"看起来太好"**。你看到 +0.039 会兴奋,不会怀疑 — 直到逐行审计代码。
2. **不可复现的结论不算结论**。cairn 文档里写的 +0.039,代码库里没有对应的可运行验证脚本。修复后重测,结论直接反转。
3. **反向因子必须按方向修正后评估**。A 股动量反转是主流效应,邻居 60 日涨多了该股后续反向下跌,这种因子 IC 是负的,但反向使用后 effICIR = |ICIR| 完全达标。一行 `direction = -1 if ICIR < 0 else 1` 把 CHAIN_MOM_60D 从"误杀"变成"通过"。
4. **证伪一个错误结论,比发布一个亮点更有价值**。+0.039 如果没被证伪,我会继续投入精力优化 GAT,在错误方向上越走越远。

详细过程见专题:[当 +0.039 的 Alpha 消失:一次 GNN 因子前视偏差的完整排查](file:///e:/各种PY程序/28-终极量化交易系统8.4/docs/自我进化框架/GNN因子前视偏差排查_20260803_知乎专栏.md)。

## 三、主线 2:open-code-review 两轮代码审查 — 11 缺陷确认,10 修复

### 为什么要做

GNN 因子的 5 个 Bug 是我自己审计发现的。这让我意识到:**代码里可能还藏着更多我自己看不出来的问题**。于是引入了阿里巴巴开源的 open-code-review 工具(v1.8.6),对核心模块做两轮独立审查。

最值得讲的是那个**高严重度正确性缺陷**:`run_daily_eod_workflow.py` 的 `log()` 函数参数传错了,导致 FeedbackLoop(反馈闭环)在**成功路径**上抛 TypeError,整个 EOD(End-Of-Day)工作流误判为失败。

这种 Bug 最毒 — 它不会让程序崩溃,只会让你以为"今天的工作流没跑成功",然后反复重跑、反复报错、反复排查,最后发现是日志函数本身的 bug。**成功路径上的错误比失败路径上的错误更危险**,因为失败路径你本来就会处理,成功路径你不会检查。

审查范围扩大到风控/执行交易/对冲/Greek/AI 决策,24 个高风险生产模块。

**确认 5 缺陷,修复 4(含 2 高严重度正确性)**:

| 高 | `greek_hedge_manager.py:208-214` | `_bs_delta` 无效输入返回 0.5(哨兵 (0,0)→N(0)=0.5)与其他 Greeks 返回 0 不一致 | 加边界检查返回 0 |

两个高严重度缺陷都值得展开:

**字段错位**:`glm5_decision_engine.py` 里 AI 信号解析时,把"紧急度"和"理由"两个字段的列位置搞反了。结果就是:AI 说"这个信号紧急度低、理由是 X",系统记录的却是"紧急度=X、理由=低"。下游风控按错误的紧急度排序,可能把不紧急的信号当紧急处理,把紧急的信号忽略。**字段错位是数据解析里最隐蔽的 bug** — 程序不报错,数据也"看起来合理",只有对照原始格式才能发现。

**Delta 哨兵不一致**:`greek_hedge_manager.py` 的 Black-Scholes Delta 计算,当输入无效(比如行权价或股价为 0)时返回 0.5(因为 N(0)=0.5 是哨兵值的默认结果)。但其他 Greeks(Gamma/Vega/Theta)在同样情况下返回 0。这导致:**遇到无效输入时,Delta 看起来"正常"(0.5 是中性对冲比例),但其他 Greeks 都归零**。对冲引擎拿到这种"假正常"的 Delta,会按 0.5 的比例去对冲一个本该跳过的无效头寸。

这两轮审查最大的价值不是"修了 10 个 bug",而是**让我意识到"自己审计"和"工具审计"是互补的**:

## 四、主线 3:iFinD 数据源全局剔除 — 给降级链瘦身

### 背景

系统的数据源降级链原本是 6 级:Wind → iFinD → 通达信 → AKShare → 新浪 → 缓存。问题是 iFinD 这一级**长期不可用**(MCP 接口不稳定),每次走到这一级都会失败然后降级到通达信 — 等于白白浪费一次网络请求和超时等待。

更糟的是,降级链里有"死节点"会制造**隐性延迟**:数据可用时没问题,数据不可用时每次都要走完整个失败链才能拿到兜底数据。在盘中行情拉取场景,这种延迟会累积成几百毫秒的滑点。

### 改动

把 iFinD 从四个地方全部剔除:

1. `utils/data_provider.py` — 移除 `_init_ifind_mcp` / `_try_ifind_mcp_realtime` / `_try_ifind_mcp_historical` + source_health 的 `ifind_mcp` 键 + 实时/历史降级链 iFinD 分支
2. `utils/data/data_layer.py` — `_DEFAULT_FALLBACK_CHAIN` 移除 ifind_mcp,docstring 重新编号 P0-P5
3. `config/settings_v510.yaml` / `settings_mac.yaml` — 配置块和 fallback_order 更新
4. `AGENTS.md` — 数据源优先级/连接器表/降级链/环境变量全部标注 iFinD 已剔除

降级链变成 5 级:**Wind > 通达信 > AKShare > 新浪 > 缓存**。

### 保留什么

`utils/ifind_client.py` 文件本身保留 — 它还有独立功能(如 `ifind_news_analyzer` / `ifind_research` 仍可能引用)。只是从核心数据降级链里剔除,不让它在每次数据请求时都制造一次失败。

**工程原则**:降级链里的每一级都必须是"真能用"的,否则就是隐性延迟。死节点必须剔除,哪怕它"看起来还在"。

## 五、主线 4:Shadow 数据修复 — 让观察期"真的在记录"

### 问题诊断

这是今天最"打脸"的发现之一。自我进化框架的观察期(Shadow Account)从 2026-07-30 启动,本来应该每天记录 daily_returns.jsonl。结果一查:

- 07-31 有数据
- 08-01 ~ 08-03 **断档三天**
- 这三天的 EOD 工作流都报 "success",但实际上数据没写进去

打个比方:你装了行车记录仪,以为在录像,结果镜头盖没打开 — 录了三天黑屏,然后让你判断这辆车安不安全。

### 根因

`utils/alpha/shadow_real_data_feeder.py` 权重加载三来源全失败:

1. `_POSITIONS_JSON` 路径错误 — 指向 `data/positions.json`(不存在),真实持仓在 `config/positions.json`
2. `config/positions.json` 的 `positions` 字段是 dict(含 `target_weight`),但 `_load_positions_json_file` 只支持直接 dict/list 格式 — 格式不匹配,解析失败
3. `trade_plan` / `strategy_plan` 因 EOD 生成脚本缺失未生成 — 第三来源也没兜住

三个来源全失败,但 `feeder` 返回了 success(因为它"成功"地跳过了),EOD 工作流就以为数据写进去了。**容错设计掩盖了根因** — 这和我此前一周在 `run_step` 里踩过的坑一模一样:脚本不存在返回 False 而非报错,静默失败。

### 修复

1. `_POSITIONS_JSON` 路径修正 → `config/positions.json`
2. `_load_positions_json_file` 新增格式 3:`positions` 为 dict 时从 `target_weight` 提取权重

### 验证 + 补录

```
dry-run: 26/26 覆盖 100%, daily_return = -0.6384%
正式补录: written = True
daily_returns.jsonl 新增: 2026-08-03: daily_return=-0.6384%, source=w13a_real_market_feed, symbols_count=26, consistency=high
```

观察数据断档修复。08-13 决策日(观察期满 14 天)终于有真实数据可依了。

### 建立防护:观察期缺失提示机制

光修这一次不够,得有机制防止再发生。新增双保险:

1. **双保险校验**:`_check_daily_returns_has_date` — feeder 返回 success 后,仍然去 `daily_returns.jsonl` 确认该日期真的写进去了(避免"feeder 成功≠写盘")
2. **失败强提示**:`_alert_observation_missing` — 控制台醒目告警(⚠️ 观察期数据记录失败 — 需手动记录)+ 手动记录 4 步指引 + EOD summary 的 `observation_alerts` 字段 + 告警文件 `reports/evolution/observation_alert_<date>.json`

```python
# 核心逻辑
feeder_success = run_feeder(date)
file_has_date = _check_daily_returns_has_date(date)  # 双保险
if not feeder_success or not file_has_date:
    _alert_observation_missing(date)  # 醒目告警 + 手动记录指引
```

**关键设计**:success 不等于写盘成功。任何"我成功了"的返回,都必须用独立的校验去确认"真的写进去了"。这是分布式系统里的经典教训,但在单机脚本里同样适用。

## 六、主线 5:自我进化框架 W1.3a/b/c 三份设计文档落地

### 背景

自我进化框架的感知层(DriftMonitor + StrategyEvaluator)之前一直在 dry_run 空数据上跑。这意味着 08-13 观察期满时,没有任何真实数据做决策依据。W1.3a/b/c 就是把感知层从"空数据预览"切到"真实数据驱动"的三步设计:

### W1.3a:Shadow Real Data Feeder(真实数据接入)

核心模块 `utils/alpha/shadow_real_data_feeder.py`(750 行),把真实行情数据按持仓权重加权,写入 `daily_returns.jsonl`:

```
真实行情数据源 (TDX)
       ↓
MarketDataProvider.get_historical_data()
       ↓
按持仓权重加权: daily_return = Σ(weight × (close/prev_close - 1))
       ↓
写入 daily_returns.jsonl (增量, 原子替换)
       ↓
DriftMonitor + StrategyEvaluator 真正"看见"市场
```

**关键设计决策**:

1. **三种权重来源自动降级**:`trade_plan → strategy_plan → positions.json`,优先用最准的
2. **三道安全护栏**:单日 |收益率| > 5% 标记 warning(不阻断但留痕)/ 数据源全失败跳过该日(不写脏数据)/ 覆盖率 < 80% 标记 `partial_coverage`(降级使用)
3. **dry_run 严格隔离**:这个踩过坑 — 第一版 dry_run 内部调用了 `feed_single_date`,结果"预览"模式下数据被写进了真实文件。重构后 dry_run 完全独立实现,绝不碰真实数据文件

**测试覆盖**:77 个单元测试,100% 通过,覆盖率 93.95%(AST 精确计算,不是 coverage.py 的粗略估计)。

### W1.3b:DriftMonitor 真实数据集成

把 DriftMonitor(漂移监控)从空数据预览切换到真实数据驱动:

- **PSI 阈值校准**:用真实数据分布校准 PSI(Population Stability Index)阈值,避免 dry_run 时代的"空分布"误判
- **真实因子漂移检测**:对比当日因子分布 vs 历史窗口分布,触发 `drift_alerts.jsonl`
- **多源交叉校验**:`cross_validate()` 方法,多数据源交叉验证异常

### W1.3c:StrategyEvaluator 真实评分

把 StrategyEvaluator(策略评估器)从空数据评分切换到真实数据评分:

- **Public/Private 分离性验证**:Public Score(可对外公布的公开指标)和 Private Score(内部真实评估)分离,检测 reward hacking(奖励黑客)风险
- **真实收益评分**:基于 `daily_returns.jsonl` 算真实 Sharpe / 最大回撤 / 胜率
- **推荐动作**:基于评分给出 `recommendation`(继续观察 / 调整 / 退役 / 重训)

### 三份文档的共同原则

1. **降级路径明确**:每个模块都有"数据不可用时怎么办"的降级路径,不静默失败
2. **真实数据 + 真实分布**:不再用 dry_run 的空分布,所有阈值都基于真实数据校准
3. **可观测性**:每个步骤都有日志、告警、文件输出,运维能看见
4. **测试覆盖**:每个模块都有单元测试,核心路径覆盖率 > 90%

## 七、几个工程上的反思

### 1. 容错设计会掩盖根因

这是今天踩了两次的坑:

- `run_step` 脚本不存在返回 False 而非报错(此前一周已发现)
- `feeder` 权重加载全失败仍返回 success(今天发现)

容错的初衷是"不让一个组件的失败拖垮整个流程",但代价是**根因被掩盖**。修复方法不是去掉容错,而是**容错 + 独立校验 + 醒目告警**:容错让流程继续,但独立校验确认结果真的对了,没对就醒目告警。

### 2. 字段错位是数据解析里最隐蔽的 bug

`glm5_decision_engine.py` 的字段错位缺陷给我敲了警钟。程序不报错,数据也"看起来合理",只有对照原始格式才能发现。

**排查方法**:对任何结构化数据解析,问自己一个问题 — **"我解析出来的字段,和原始格式的列定义对得上吗?"** 如果不确定,就写一个对照测试,把原始格式和解析结果同时打印出来,人工对照一遍。

### 3. 降级链里的死节点必须剔除

iFinD 长期不可用却留在降级链里,每次数据请求都浪费一次失败 + 超时。这种隐性延迟在数据可用时看不出来,在数据不可用时累积成几百毫秒滑点。

**原则**:降级链里的每一级都必须是"真能用"的。定期清理死节点,哪怕它"看起来还在"。

### 4. 自己审计和工具审计是互补的

GNN 的 5 个 Bug 是我自己审计发现的(工具没报,因为它们是逻辑错误);这 11 个缺陷是工具报的(我自己没看出来,因为它们藏在我不熟悉的模块里)。

**人擅长抓逻辑错误,工具擅长抓规则违规**。两者结合,覆盖率最高。单一来源都会漏。

### 5. success 不等于写盘成功

Shadow 数据断档三天的根因:feeder 返回了 success,但数据没写进文件。

**分布式系统的经典教训**,但在单机脚本里同样适用。任何"我成功了"的返回,都必须用独立的校验去确认"真的写进去了"。这次新增的 `_check_daily_returns_has_date` 就是这个原则的落地。
