## 二、因子评估的"时间维度"：从单点到时序

### 2.1 单点 IC 的问题

IC（Information Coefficient）衡量因子值与未来收益的相关性。之前的实现用"过去收益近似未来收益"——把 T-5 到 T-1 的收益当作 T 时刻的 forward return，与 T 时刻的因子值算 Spearman rank IC。

问题在于，过去收益和未来收益之间存在自相关。用一个自相关序列算出来的 IC，会系统性高估因子的预测能力。好因子被夸上天堂，坏因子也看起来"还行"。

这就像用昨天的天气预测今天的天气——大部分时候对的，但这不代表你的预测模型有多厉害。

### 2.2 时序 IC/ICIR 的正确姿势

U1 的修复方案：复用 `factor_history_builder` 已产出的日频因子序列，逐日计算横截面 IC，再汇总为 ICIR。

```
单点 IC（旧）:  IC = Spearman(factor_T, return_T-5_to_T-1)  ← 自相关污染
时序 IC（新）:  IC_series = [Spearman(factor_t, forward_return_t) for t in dates]
               ICIR = mean(IC_series) / std(IC_series)
```

关键设计：IC_IR 为负时自动反向使用因子。这与 VT_MICRO_VOL_SKEW 的反向信号方法学对齐——IC_IR=-0.42 的因子反向使用后变成 +0.42，"毒药"变"解药"。

### 2.3 双模式降级

时序 IC 需要因子历史序列。如果 `factor_history` 不存在（比如新因子刚上线），自动降级为单点 IC，保证向后兼容：

```python
def evaluate_factors(factor_values, returns, factor_history=None):
    if factor_history is not None and len(factor_history) >= 10:
        # 时序模式: 逐日横截面 IC → ICIR
        ic_series = calc_ic_series_from_history(factor_history, returns)
        ic_ir = calc_ic_ir(ic_series)
    else:
        # 降级模式: 单点 IC（保留旧行为）
        ic_ir = calc_ic_single_point(factor_values, returns)
    return ic_ir
```

21 个测试覆盖：时序 IC 正确性、ICIR 计算、降级模式、反向因子处理、与 `gate1_validation` 结果一致性。全部通过。

## 三、回测引擎的"现实约束"：涨跌停与停牌

### 3.1 一个被忽视的漏洞

回测引擎的 `run()` 方法早就支持 `limit_up_prices`、`limit_down_prices`、`suspended` 三个字段——涨停禁买、跌停禁卖、停牌冻结。但数据源从未提供这些字段，约束一直处于"有开关无电流"的状态。

这意味着回测里你可以在涨停板上买入、在停牌日卖出——一个完美的"纸上富贵"陷阱。

### 3.2 A 股涨跌停规则全覆盖

U2 新增 `price_limit_calculator.py`，覆盖全板块规则：

| 板块 | 涨跌停 | 代码前缀 |
|------|--------|---------|
| 主板 | ±10% | 60/00 |
| ST 股 | ±5% | 60/00 + ST 标记 |
| 创业板 | ±20% | 300/301 |
| 科创板 | ±20% | 688/689 |
| 北交所 | ±30% | 8/4 |
| ETF | ±10% | 159/510 等 |
| 可转债 | 无限制 | 113/123 等 |

价格计算用 `Decimal` + `ROUND_HALF_UP` 四舍五入到分——不是 `float` 的银行家舍入，避免一分钱的误差在批量回测中累积。

### 3.3 停牌检测不误判一字板

停牌检测的朴素思路是"volume=0 就是停牌"。但一字涨停板也是 volume=0（开盘即封死，无成交）。如果误判为停牌，回测会冻结一个本该涨停的标的。

解决方案：`volume=0` 且 `open=0`（停牌无开盘价）或 `price ≤ 0` 才判定停牌。一字板 `open > 0`（有开盘价，只是无成交），不误判。

67 个测试覆盖：全板块涨跌停价计算、ST 标记、停牌检测、一字板排除、BacktestDataLoader 集成、回测引擎约束生效。全部通过。

## 四、除权日的"跳空消除"：复权因子对齐

### 4.1 一个 13% 的虚假亏损

某 ETF 持仓成本 1.50 元，除权日收盘 1.30 元。未复权口径下，当日盈亏 = (1.30 - 1.50) / 1.50 = -13.3%。但这 13.3% 不是真亏了——分红除权导致价格自然下跌，实际持仓价值不变。

如果用这个 -13.3% 喂给漂移检测，系统会认为策略出了大问题；如果喂给 DSR 评估，Sharpe 会被严重低估。

### 4.2 数学等价的对齐方案

U3 的修复：用 akshare `stock_zh_a_daily(adjust="hfq-factor")` 获取后复权因子，把未复权价格对齐到 hfq 基准：

```
aligned_prev_close = prev_close × (yesterday_factor / today_factor)
aligned_daily_pnl_pct = (today_close - aligned_prev_close) / aligned_prev_close
```

数学上等价于直接用 hfq 价格算收益，但保留了原始价格字段供调用方按需取用。除权日 `aligned_daily_pnl_pct ≈ 0`，跳空消失。

### 4.3 零行为变更的工程纪律

`pnl_calculator.calculate_pnl` 新增 `align_hfq: bool = False` 参数。默认 False，行为完全不变——现有调用方无感知。需要除权日对齐的调用方显式开启：

```python
# 旧调用（不变）
result = calculate_pnl(positions, market_data)

# 新调用（启用对齐）
result = calculate_pnl(positions, market_data, align_hfq=True, hfq_date="2026-08-05")
```

56 个测试覆盖：零行为变更、非除权日仅注入因子、除权日 aligned_daily_pnl_pct≈0、除权日 aligned_cost_price 对齐、provider 不可用降级、单标的失败不影响其他。全部通过。

## 五、E2E 测试的"最后一公里"：Pipeline + Shadow

### 5.1 一个 access violation 的幽灵

U5 补齐两条 E2E 测试链路：`full_pipeline`（PipelineOrchestrator 完整周期）和 `shadow_account_lifecycle`（ShadowAccountAdapter 生命周期）。

写测试时遇到一个诡异的崩溃：`alpha_pipeline.py` 第 38 行 `from qlib.contrib.model import LGBModel` 触发 `lightgbm → scipy.sparse → _isolve/iterative.pyd` 加载时，Windows 进程直接崩溃，exit code 3221225477（access violation）。

诡异之处在于：`alpha_pipeline.py` 这行代码本身包在 `try/except ImportError` 里，但 **Windows access violation 不可被 Python try/except 捕获**——进程直接挂了，连 except 都来不及执行。

### 5.2 sys.modules 拦截器

解决方案不在 `alpha_pipeline.py` 里改（那里改不了），而在 `conftest.py` 顶部注入一个 `ImportBlocker`，把 `qlib`、`qlib.contrib`、`qlib.contrib.model`、`lightgbm` 四个模块塞进 `sys.modules`，让 `from qlib.contrib.model import LGBModel` 直接从 `sys.modules` 拿到拦截器，触发 `ImportError`，走降级分支（`_QLIB_AVAILABLE=False`）。

```python
class _ImportBlocker:
    def find_module(self, name, path=None):
        if name in BLOCKED_MODULES:
            return self
    def load_module(self, name):
        raise ImportError(f"Blocked by test isolation: {name}")

sys.meta_path.insert(0, _ImportBlocker())
```

这是 Python import 机制的"白帽"用法——不改生产代码，只在测试环境拦截危险导入链。

## 六、Shadow 账户的"状态断层"根治

### 6.1 一个 5 天 vs 7 天的谜题

U1-U5 补完地基后，Shadow 账户的日常运维也暴露了一个问题。

`daily_returns.jsonl` 有 7 条真实日收益（07-27 ~ 08-04），但 `shadow_state.json` 的 `daily_nav` 只有 5 条，全部卡在 1.016482（+1.65%），最后更新停在 07-31。

这就是之前"3 天零收益均为数据问题占位值"的真相——feeder 脚本成功写入了真实收益到 jsonl，但没有任何脚本把 jsonl 同步回 `shadow_state.json` 的 `daily_nav`。

### 6.2 三级修复

**第一级：状态重建**。新增 `rebuild_shadow_state_from_returns.py`，从 `daily_returns.jsonl` 的 7 条真实收益，用 `nav = nav × (1 + daily_return)` 从 1.0 累乘重建 `daily_nav`。重建后净值从虚假的 1.016482 回归真实的 0.996477（累计 -0.35%），最大回撤 0.70%，Fail-Fast 未触发。

**第二级：配置补齐**。`shadow_admission_launcher.py daily` 运行失败——ConfigManager 4 级路径都找不到 `shadow_admission` 配置。根因是配置文件从未创建。补建 `shadow_admission.yaml`（含 3 个待准入模块、Fail-Fast 3%/5% 阈值、准入标准 DSR≥0.5/年化≥15%/回撤≤10%）。

**第三级：模块补齐**。配置加载成功后，`ShadowAccountAdapter` 初始化又报 `ModuleNotFoundError: No module named 'shadow_account_system'`——提供 `ShadowAccount` + `FailFastMonitor` 的核心模块从未实现。补建 `shadow_account_system.py`（AccountStatus 枚举 + FailFastMonitor 回撤检查 + ShadowAccount 净值记录），实现 adapter 依赖的全部接口。

### 6.3 EOD 工作流集成

根治方案：把状态重建集成到 EOD 工作流主链路。在 `run_daily_eod_workflow.py` 的阶段编排中，阶段四点五（feeder 写入 jsonl）之后、阶段四点七（漂移检测读取 jsonl）之前，新增**阶段四点五B：Shadow 状态同步**：

```
阶段四点五: Shadow 收集 (feeder → daily_returns.jsonl)
    ↓
阶段四点五B: 状态同步 (rebuild → shadow_state.json)  ← 新增
    ↓
阶段四点七: 漂移检测 (drift_integrator → IC/ICIR)
```

设计三条安全线：
1. **前置依赖检查**：phase4_5 未成功时自动跳过（避免用旧数据重建）
2. **fail-safe**：失败不中断 EOD 主流程，仅 WARN
3. **`--skip-shadow` 统一控制**：一个参数同时跳过 4_5/4_5B/4_7 三个 Shadow 相关阶段

3 个测试验证全部通过：skip-shadow 跳过、前置依赖检查跳过、正常执行重建。

从此每日 15:30 EOD 工作流自动同步状态，无需人工干预。
