## 1. 审查标准（审什么、怎么判级）

### 1.1 通用分级标准

| 级别 | 定义 | 判定示例 | 处置 |
|------|------|----------|------|
| 🔴 **阻断（Blocker）** | 不修复不得合入/不得进入生产 | 安全漏洞、资金损失风险、数据损坏、API 契约破坏、关键路径缺错误处理、竞态/死锁 | 立即修复，阻塞合入 |
| 🟡 **建议（Should Fix）** | 应当修复，可限期 | 输入校验缺失、命名不清、重要行为无测试、性能问题（N+1 查询等）、重复代码未抽取 | 限期修复（默认 5 个交易日内） |
| 💭 **细节（Nit）** | 可选改进 | 风格不一致（linter 未覆盖处）、文档缺口、备选方案建议 | 随下轮顺手修，不追踪 |

### 1.2 🔴 阻断项检查清单（合入前逐条过）

**正确性**
- [ ] 逻辑与需求/文档一致，边界条件（空集合、NaN、极端值、除零）已处理
- [ ] 时区/交易日历处理一致（统一 CST/UTC+8，参考 t57 日期断言教训）
- [ ] 幂等性：同日重跑不产生重复副作用（参考 B4 shadow 幂等 bug 教训）

**安全**
- [ ] 无 SQL 字符串拼接（B608）— 参数化查询或验证后 `# nosec` 注记
- [ ] 无 shell=True 注入面（B602/B603），subprocess 一律参数列表形式
- [ ] pickle 反序列化仅限可信来源 + SHA256 校验（B301）
- [ ] XML 解析用 defusedxml 或确认输入可信（B314）
- [ ] API Key/密钥不出现在代码/日志/报告（.env + python-dotenv 约束）

**资金安全（量化系统专项）**
- [ ] 风控路径 fail-closed：异常时拒绝交易而非放行（PreTradeGuard/KillSwitch BLOCK 模式）
- [ ] 交易金额/数量计算有精度保护（不裸用 float 直接算钱，用 safe_math）
- [ ] 订单生命周期终态可达（无卡死态），超时撤单逻辑存在
- [ ] 回撤熔断阈值与配置一致，降级路径明确

**回测诚实性（量化系统专项）**
- [ ] 无前视偏差：特征只能用 t-1 及以前数据（ci_lookahead_guard 通过）
- [ ] 无幸存者偏差：universe 构建含退市标的处理
- [ ] 复权口径明确（前复权/后复权，参考 P2.2 sina 未复权失真教训）
- [ ] 成本模型含滑点/佣金/冲击成本，涨跌停/停牌约束已接入

**可维护性**
- [ ] 宽泛 `except Exception` 必须带 `# fail-safe` 标注且降级行为明确（R10/T6 口径）
- [ ] 新文件 ≤800 行（QC-2.1 标准），超大文件拆分走 D10 门禁（≤2000）
- [ ] 模块入口有 docstring + 关键函数有类型注解（ANN 规则）

### 1.3 🟡 建议项检查清单（抽查重点）

- [ ] 公共函数参数/返回值类型完整（ANN001/ANN201 清零）
- [ ] print 已转 logger（T201 清零，scripts/ 豁免目录除外）
- [ ] 网络请求有 timeout + 重试 + 降级链
- [ ] 文件写入用原子写（temp + replace/move，参考 WinError 5 教训用 shutil.move）
- [ ] 重要分支有单元测试，覆盖率不使全局基线退化（T8 门禁）
- [ ] 命名表意清晰，无魔法数字（配置化）

### 1.4 审查评论格式（给审查者）

```
🔴 **[类别] 一句话标题**
文件:行号 — 问题描述。

**为什么**: 触发条件 + 后果（资金/正确性/维护性影响）。

**建议**: 具体改法（可直接落地的代码方向）。
```

要求：每条评论必须「具体到行 + 解释为什么 + 给出建议」，不允许只说"有安全问题"。意图不明时先提问再判定，不预设是 bug（二次核验铁律）。

## 2. 审查流程（四层防线）

### 2.1 流程总览

```
代码变更
   │
   ▼
L0 机检门禁（自动，每次 commit/PR）
   │  ruff + bandit(-ll) + mypy 基线 + pytest 增量 + ci_integrity_check
   │  ── FAIL → 拒绝合入，回到修复
   ▼
L1 增量人审（每次 PR，≤400 行 diff）
   │  审查者按 §1.2 清单过 diff + 变更文件不超过 10 个
   │  ── 🔴 未清零 → 打回
   ▼
L2 模块深度审（触发式：新模块 / 改风控·执行·回测核心链路 / >800 行变更）
   │  code-review-graph MCP + 五轴审查（正确性/安全/维护/性能/测试）
   │  ── 产出审查报告，沉淀 cairn/<topic>.md
   ▼
L3 独立审计（触发式：发版前 / 大规模重构后 / 交叉审计）
   │  独立报告 + 强制二次核验（任何 P0 清零前必须代码交叉验证）
   │  ── 勘误写进同文档，不漂移
   ▼
每日 EOD 巡检（自动）
   │  engineering_debt_gate（25 项）+ mypy_baseline_gate + 覆盖率趋势
   └── RED → 冻结新功能，优先还债
```

### 2.2 L0 机检门禁（自动防线，零人工）

| 检查 | 工具/脚本 | 通过标准 | 挂接点 |
|------|-----------|----------|--------|
| Lint | `ruff check .` | 0 违规（默认配置含 per-file-ignores） | quality-gate.yml（PR 增量）+ 每日 |
| 安全 | `bandit -r utils/ reporting/ ai_decision/ scripts/ quant_modules/ -ll` | High=0 且 Medium 新增=0 | 每日 EOD |
| 类型 | `scripts/mypy_baseline_gate.py` | 错误数 ≤ 基线（禁止增量） | **每日 EOD（本次新增挂接）** |
| 测试 | `pytest`（增量选择 `_select_tests_by_diff.py`） | 变更相关测试全绿 | PR + 每日 |
| 工程债 | `scripts/engineering_debt_gate.py` | 非 RED | 每日 EOD |
| 工作区 | `git status --porcelain \| wc -l` | 未提交变更 ≤50 | 每日 EOD（本次新增） |

**关键规则**：
1. **基线只许降不许升** — mypy/覆盖率/工程债基线更新必须走 `--update` 显式操作并在 LOG 留痕，禁止静默漂移。
2. **新脚本无豁免权** — 任何新目录/新文件默认全量过 ruff；确需豁免必须写入 ruff.toml 的 per-file-ignores 并说明理由。
3. **提交前自检** — `ruff check . && bandit -ll && pytest <变更相关>` 三连跑绿后才允许 commit。

### 2.3 L1 增量人审（PR 防线）

- **触发**: 每次 commit/PR，diff ≤400 行、涉及文件 ≤10 个
- **审查者**: AI 审查助手（ocr/code-review）优先 + 人工抽查风控与资金路径
- **时限**: 当日完成（交易日 15:30 后批量处理）
- **重点**: 按 §1.2 清单核对；**资金路径（下单/风控/再平衡）与回测引擎的变更升级为 L2**
- **产出**: 审查评论（§1.4 格式），🔴 必须清零才能合入

### 2.4 L2 模块深度审（触发式防线）

**触发条件（任一）**：
1. 新建模块/包（如 Wave 6 新增 12+ 生产模块）
2. 修改核心链路：风控六件套（T09-T14）、实盘执行（T15-T18）、回测引擎、信号融合
3. 单次变更 >800 行或跨 >10 文件

**方法**：
- 优先用 code-review-graph MCP（见 `cairn/code-review-graph-guide.md`）做依赖与影响面分析，不裸 Grep
- 五轴审查（QC-2.3 已接入）：正确性 / 安全 / 可维护性 / 性能 / 测试覆盖
- 量化专项：前视偏差扫描 + fail-closed 行为验证 + 复权口径核对

**产出**: 审查报告归档 `docs/代码审查报告_<模块>_<日期>.md`，结论沉淀 `cairn/<topic>.md`，LOG 追加条目。

### 2.5 L3 独立审计（终极防线）

**触发条件**: v8.7 等发版前 / 大规模重构完成后 / L2 发现系统性问题。

**铁律（源自 2026-08-08 实战教训，`cairn/code-review-independent-audit-20260808.md`）**：
1. **任何 P0 进清零配额前必经二次核验** — 独立报告的 P0 结论必须代码交叉验证（历史上 3 处误判：字符串注解≠运行时错误、离线脚本≠实盘链路、"语法崩溃"误报）
2. **勘误写进同文档不漂移** — 更正注记原位追加，不静默覆盖
3. **运行时验证优先于静态推断** — 用 py_compile / import / 小样本执行验证，不以注解形态下结论

### 2.6 每日 EOD 巡检（常态化防线）

挂接到 `15_每日工作流/run_daily_eod_workflow.py`（在审计阶段执行，失败不阻断 EOD 主流程）：

```bash
python scripts/engineering_debt_gate.py          # 25 项工程债
python scripts/mypy_baseline_gate.py             # 类型基线（本次建议新增挂接）
python scripts/ci_integrity_check.py --strict    # CI 脚本完整性
bandit -r utils/ reporting/ ai_decision/ scripts/ quant_modules/ -ll   # 安全增量
git status --porcelain | wc -l                   # 工作区卫生（本次建议新增）
```

巡检结果写入每日报告的「代码质量」小节；RED/BLOCK 状态次日晨会优先处置。

## 3. 审查角色与职责

| 角色 | 承担 | 决策权 |
|------|------|--------|
| L0 机检 | CI/定时任务 | 自动拒绝（硬门禁） |
| L1 审查者 | AI 审查助手 + 值班人 | 🔴 打回权 |
| L2 审查者 | 代码审查专家（本角色）+ 模块负责人 | 架构级否决权 |
| L3 审计 | 独立审计人（非原实现者） | 发版阻断权 |
| 项目负责人 | 用户 | 铁律例外审批（如交易时段紧急修复） |

## 4. 时序纪律（量化系统特有）

1. **交易时段（09:15-15:00）禁止**: 大文件拆分、跨模块重构、依赖升级、核心链路行为变更。只允许: 读操作、测试补齐、文档。
2. **非交易时段执行**: 重构类任务必须 DRY-RUN 对照 + 单测全绿 + I/O 对比（bit-for-bit）。
3. **发布冻结窗（12-10 起）**: 仅允许修复类变更，且每次变更需 🔴 清零证明。
4. **紧急修复通道**: 交易时段发现资金安全 bug 可热修，但必须: 当日补审查 + 次日 L2 复审 + LOG 留痕。
