## 二、G1：归因数据真实性修复（P0，零侵入）【已完成 2026-09-02】

### 2.1 现状与缺口

| 项 | 证据 | 状态 |
| --- | --- | --- |
| EOD 调用点 | `15_每日工作流/run_daily_eod_workflow.py:1744` → `run_phase4_55_attribution()`（L1004） | 已挂链路，每日执行 |
| 引擎 | `utils/pnl_attribution_engine.py`（L1029 导入，L1082 落盘） | 正常产出 |
| **输入数据** | **L1047-1078 硬编码合成常量** | **P0 缺陷** |
| 产物流 | `reports/pnl_attribution/pnl_attribution_{date}.json`（12 份，08-18 ~ 09-01） | 产出稳定但数值失真 |

合成数据明细：

```python
benchmark_returns = [portfolio_ret * 0.8]        # 基准收益 = 组合收益 x 0.8
factor_returns    = {k: [portfolio_ret * c]}     # 因子收益 = 组合收益 x 固定系数
sector_returns    = {k: [portfolio_ret * c]}     # 行业收益 = 组合收益 x 固定系数
trading_costs = 0.0, funding_cost = 0.0          # 交易成本恒为 0
```

**风险定性**：归因报告每天正常产出、字段齐全、无告警，但所有维度都是组合收益的算术变形。它让"模型赚钱还是行情赚钱"得到**确定但错误**的答案 —— 比没有归因更危险（不会触发任何人的怀疑）。

### 2.2 真实数据源可得性（已核验）

| 维度 | 现有真实数据源 | 位置 | 接入方式 |
| --- | --- | --- | --- |
| 交易成本 | FillsStore 成交回报事实源（有成交走成交）→ TCA 引擎降级估算 | `utils/execution/fills_store.py`、`utils/tca_engine.py`、`utils/tca_post_trade_attribution.py` | 直接接入 |
| 交易成本（备选） | 报告阶段已有真实实现 `sum(amount × 0.001)` | `v8.3_institutional/workflow/phases/report.py:412` | 可复用口径 |
| 因子 / 行业收益 | Barra 10 风格 + 8 行业真实归因（48KB，已实现**但未被 EOD 调用**） | `utils/attribution/factor_attribution.py`、`utils/attribution/brinson_attribution.py` | 改调用，不重写 |
| 期权保护 | 真实 EOD 报告注入（`_load_hedge_pnl_from_eod_report()`），但 12 份中 9 份为 0 | `utils/pnl_attribution_engine.py:998` | 需排查零值根因 |
| 基准收益 | **待补** —— 需接入指数行情（沪深 300 / 中证 500 或组合自定义基准） | — | 新增数据源接入 |
| 择时 | 现为残差插补 `timing_pnl = total_pnl - explained` | `utils/pnl_attribution_engine.py:230-240` | 先正名，后可选建模 |

### 2.3 设计方案

1. **新建 `utils/attribution/real_inputs_builder.py`（或在 `daily_panel.py` 内扩展）**
   统一构建真实归因输入，返回 `{benchmark_returns, market_returns, factor_returns, sector_returns, trading_costs, funding_cost, hedge_pnl}`。
   - 基准收益：接指数数据源（可复用现有行情链路），失败时 **fail-closed 标记 `attribution_degraded=True`** 并在报告中显式标注，绝不回落合成值
   - 因子/行业收益：调用 `factor_attribution.attribute_from_positions()` 真实计算
   - 交易成本：优先 FillsStore 当日真实成交 → 无成交回落 TCA 估算（沿用 fills_pnl_bridge 的"有成交走成交"模式）
2. **改造 `run_phase4_55_attribution()`（L1047-1078）**：删除全部合成常量，改为调用输入构建器；构建失败时 `attribution_degraded=True` + 告警 + 不产出归因报告（fail-open 落审计，但**不产出失真数字**）
3. **统一行业分类映射表**：EOD 传 6 个中文行业 vs 引擎 `SECTORS` 11 个不匹配（当前仅 4 个命中，其余 `factor_return: 0.0`）。建立 `symbol → 引擎行业` 映射，命中率目标 100%
4. **`timing_pnl` 正名**：重命名为 `unexplained_pnl` 并在报告注明为"未解释残差"（非择时收益）。真实择时归因列为可选后续项
5. **一致性校验**：断言 `sum(各维度) ≈ total_pnl`（容差 1%），不符则告警 —— 防止修复后再次出现口径漂移
6. **回归测试**：新增"输入非合成"断言测试（检测硬编码系数），确保修复不回退

### 2.4 验收标准

- [ ] 六维度输入全部来自真实数据源，L1047-1078 合成常量清零
- [ ] 交易成本字段非零（有成交日必 > 0）
- [ ] 行业命中率 100%（无 `factor_return: 0.0` 的未命中行业）
- [ ] 连续 5 个交易日归因数值与独立复算偏差 < 1%
- [ ] 一致性校验（各维度和 ≈ 总 PnL）连续 5 日通过
- [ ] 基准数据缺失时 fail-closed：不产出归因报告 + 告警，不回落合成值
- [ ] 门禁三件套无回归

## 三、G2：Chaos 灾难演练（P0，零侵入，唯一新建项）【已完成 2026-09-02】

### 3.1 现状与缺口

### 3.2 可复用的既有安全机制（断言基准）

| 机制 | 位置 | 可断言行为 |
| --- | --- | --- |
| 数据降级 → 暂停建仓 | `build_plan_executor.get_emergency_protocol`（M-1 修复，`data_degraded` → `day_capital_multiplier=0.0`） | 数据异常时**不下单** |
| 熔断 / Kill Switch | `utils/risk/` T11 IntradayCircuitBreaker、T12 KillSwitchManager | 连续失败触发熔断 |
| 实盘下单四道门 | T15 LiveOrderExecutor（T09→T10→T12→T11，fail-closed） | 任一门不过则拒单 |
| 订单生命周期 | T16 OrderLifecycleTracker（超时撤单 / 孤儿单检测） | QMT 断开时不留孤儿单 |
| 降级审计 | `utils/degradation_audit.py` | 所有降级可追溯 |

### 3.3 设计方案

**新建 `utils/chaos/fault_injector.py`** —— 故障注入器，统一注入接口：

| 场景 | 注入方式 | 期望安全状态（断言） |
| --- | --- | --- |
| 1. Wind 断开 | 主数据源全部抛异常 | 降级链生效（Wind MCP → akshare → sina）；全失败则 `data_degraded=True` → 暂停建仓，不下单 |
| 2. QMT 断开 | broker 连接失败 / 下单超时 | 拒单 + T16 超时撤单 + 无孤儿单 + 告警；不重试到裸实盘 |
| 3. 数据错一天 | 注入未来日期行情 / 日期错位 | 非单调时间戳检测（`NonMonotonicTimestampError`，W6.3 已实现）拦截；不产生前视信号 |
| 4. ETF 停牌 | 标的标记停牌 | PreTradeGuard `SUSPEND_FILTER` 拦截该标的；其余标的不受影响 |
| 5. 期权无法成交 | 期权订单全拒 / 零流动性 | 期权对冲降级 + 组合敞口告警；不无限重试；有审计留痕 |
| 6. 模型输出异常 | 信号 NaN / 极端值 / 全零 | 信号层 fail-closed（不产生订单）+ 告警；不以 NaN 下单 |

**新建 `tests/chaos/test_chaos_trading.py`** —— 六场景用例，每个用例三段式：注入 → 运行链路 → 断言安全状态。

**通用断言模板**（所有场景）：
1. 不产生未受控的真实订单（决策路径 fail-closed）
2. 有降级审计留痕（`degradation_log.jsonl` 或风控审计）
3. 有告警发出（不静默失败）
4. 系统未崩溃（fail-safe 而非 crash）

### 3.4 验收标准

- [ ] 六场景全部有用例且通过
- [ ] 任一故障注入后：无裸下单、无静默失败、有审计、无崩溃
- [ ] 用例可被 CI 稳定执行（不依赖真实网络 / 不依赖真实账户）
- [ ] 与既有 `test_data_layer_chaos.py` 无冲突，风格一致

## 四、G3：风险预算 regime 打通 + 资产大类映射（P1，**侵入生产链路 → shadow 先行**）

### 4.1 现状

| 模块 | 能力 | 状态 |
| --- | --- | --- |
| `utils/risk_budget_engine.py` | 事前 VaR 校验：组合 VaR95/99 + 单标的 VaR + 集中度 + 回撤预算 + 预算使用率 | 阈值**静态**（max_daily_var_95=0.035 / max_single_var_95=0.012 / max_drawdown=0.15 / max_weight=0.15），**无 regime 输入** |
| `utils/alpha/vol_regime_weighter.py`（1033 行） | `sense_regime(vix, daily_returns, psi, drawdown)` 多指标 + 一致性校验 → 风格权重乘子 → 约束（单票/行业/现金下限）→ 建议落盘 → `apply_to_portfolio(yaml_path, dual_signature)` 需双签 | **已启用**（`config/feature_flags.yaml:36` `USE_VOL_REGIME_WEIGHTER: default: true`） |

**缺口精确定义**：
1. VaR 侧（风险校验）与配置侧（regime 响应）**两套能力未打通**，无数据流串联
2. 缺 `regime → {股票, ETF, 期权保护}` **资产大类三分类预算映射表**（审查的 Bull 80/15/5、Normal 60/30/10、Crisis 20/50/30）；现有为风格权重乘子 + 防守/进攻 boost，层面不同

### 4.2 设计方案

1. **新建 `config/risk_budget_regime.yaml`** —— regime → 资产大类预算映射 + 各 regime 下的 VaR 阈值：

   | regime | 股票 | ETF | 期权保护 | max_daily_var_95 | 判定依据 |
   | --- | --- | --- | --- | --- | --- |
   | Bull | 80% | 15% | 5% | 放宽 | 复用 `sense_regime` 输出 |
   | Normal | 60% | 30% | 10% | 基准 | 同上 |
   | Crisis | 20% | 50% | 30% | 收紧 | 同上 |

   > 具体数值为**待校准初值**，须用历史数据回归校准后冻结（禁止直接采用审查建议值而不验证）。

2. **新建 `utils/risk_budget_regime_bridge.py`** —— 桥接层（不改老模块内脏）：
   - 输入：`VolRegimeWeighter.sense_regime()` 的 regime 标签
   - 查 `config/risk_budget_regime.yaml` → 产出 (a) 资产大类预算 (b) `RiskBudgetEngine` 的动态阈值
   - 输出供组合层 / 风控层消费

3. **`RiskBudgetEngine` 增加可选 `regime` 参数**（向后兼容，不传则用现有静态阈值）—— 最小侵入改造

4. **shadow 模式先行**（比照 MVSK P5-1 模式）：
   - 新建 `apply_regime_budget_shadow()`：只记录不生效，落盘 `reports/shadow/risk_budget_regime_diff.jsonl`（记录 regime 判定、建议预算、与当前实际配置差异）
   - shadow ≥7 天 + 无异常换仓 + Δ夏普无恶化 → 双签启用

5. **审计**：regime 切换记录（时间、指标、前后预算、触发原因）
