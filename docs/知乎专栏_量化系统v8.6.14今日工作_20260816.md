### NB-1 [High] broker 告警路径 TypeError：fail-open 设计反成崩溃点

```python
# broker_factory.py L30-36（修复前）
def _safe_send_alert(message: str, level: str = "WARNING") -> None:
    try:
        from utils.notify import send_alert
        send_alert(content=message, level=level)        # ← 缺必填 title!
    except (ImportError, AttributeError):               # ← 不含 TypeError
        logger.warning("[broker_factory] %s: %s", level, message)

# notify.py 实际签名：def send_alert(title: str, content: str, ...)
```

`send_alert(title, content, ...)` 的 `title` 是必填位置参数，而 `_safe_send_alert` 只传了 `content` 和 `level` → 每次调用必抛 `TypeError`。except 元组只捕 `(ImportError, AttributeError)`，TypeError 直接穿透——"绝不静默"的兜底函数本身成为崩溃源。

**影响面**：`get_broker` 全部告警路径（配置读取失败/dry_run 影子模式/TRADING_ENV 降级/SimulatedBroker 构造失败）。**生产实盘场景下 broker 启用 + dry_run=true 时，`get_broker()` 直接抛 TypeError，下单链路入口崩溃**。

# alpha_pipeline.py L461-478（修复前）
def _inject_to_fusion(self, signal_result: AlphaSignalResult) -> None:

## 五、模式结论与工程启示

### 模式结论：BLE001 精确化的副作用

本轮 6 个 Bug 的共性是"错误处理/降级路径自身带病"。根因可追溯到 W7.1.2 期间的 live_scheduler BLE001 精确化批量修改：

- 原始代码：`except Exception` 兜底（BLE001 违规）
- 精确化：收窄为 `except (ValueError, KeyError, ...)` 元组
- 副作用：**未核对 try 块的 raise 面**，TypeError/ImportError/RuntimeError 被误删

**教训**：BLE001 精确化不能机械收窄，必须逐个核对 try 块内所有可能抛出的异常类型。降级路径（fail-open/fail-safe）自身的健壮性比主路径更关键——因为降级路径是"最后一道防线"，它崩溃时主路径已经崩溃，系统将完全失去兜底能力。

### 工程启示

1. **全量门禁 vs 分批子集**：分批跑测试会掩盖跨模块依赖问题，必须定期跑全量
2. **降级路径健壮性**：`_safe_send_alert` 这类兜底函数自身的崩溃比主路径崩溃更危险
3. **异常元组精确化**：收窄 except 元组时必须核对 try 块 raise 面，不能机械替换
4. **导入完整性**：F401 检查能发现未使用 import，但 F821（未定义名称）在运行时才触发，需静态检查 + 运行时测试双保险
5. **测试债 vs 真实 bug**：测试失败不能一律归类为"测试债"，需逐个甄别（如 daily_panel FeatureFlags 签名漂移实为生产代码 bug）
