> **性质**：登记观察项的准入裁决材料，非实施计划。
> **上游约束**：ROADMAP §2027 PLAN「GitHub 集成全部后置 2027，冻结期内零引入」＋ 09-02 决策 2「2027 前不引入新框架」＋ Q4 冻结窗（09-19~12-10）。

## §0 裁决

**结论：vnpy 劝退，不进入 2027 候选池实施序列。**

判据命中「已有替代」——且替代方案（QMT/xtquant）不是计划中的未来项，而是**已在生产执行链路上就位**的现存实现。

## §1 修订声明（重要）

本文修正 2026-09-05 同日会话中的一项**错误建议**。该建议基于 `docs/高价值项目接入落地指南_20260809.md` §3.2，原文为：

> 「**vnpy —— 实盘执行替换（缺失，P0）**
> 目标：用券商 CTP/API 程序化下单，替代 `pyautogui/pywinauto` 点击同花顺 GUI（脆弱、慢、怕界面变动）。」

经代码实测，该条目的**问题陈述不成立**，两个前提均被证伪：

### 1.1 「GUI 点击下单是生产路径」——证伪

| 核对项 | 结果 |
|---|---|
| `pyautogui` / `pywinauto` 全仓 import 点 | 仅 `utils/execution/broker_adapters.py` **注释内**出现（`from pywinauto import Application` 为注释掉的占位代码）。无任何真实 import |

**补充说明（2026-09-05 二次核实，避免反向过度解读）**：虽然 pywinauto 本身从未被 import，但
`ThsBrokerAdapter(mode="gui")` **代码分支是真实存在且被测试覆盖的**
（`tests/unit/test_g7_broker_adapters_boost.py` 中 `test_connect_gui_with_path` 等 8+ 处断言）。
因此「GUI 自动化未接线」的正确含义是：**该分支存在但从未实现**，而非「该分支不存在」。
清理动作只能是注释级标注，**不得删除分支**（会破坏测试并移除未实现能力的记录）。
| 生产执行链路引用 | `daily_trade_executor.py` / `alpha_hedge_engine.py` / `stop_loss_monitor.py` 均**零引用** |
| 结论 | GUI 自动化**从未真正接线**，只是历史占位注释，不存在「替换」这一动作的对象 |

### 1.2 「程序化下单通道缺失」——证伪

现存实现（均早于本建议）：

| 组件 | 路径 | 状态 |
|---|---|---|
| 统一券商装配点 | `utils/execution/broker_factory.py` | ✅ 2026-08-09 接线（G1 QMT 真实下单） |
| QMT 本地直连 | `ms_strategy/src/execution/qmt_broker.py`（`QmtBrokerAPI`） | ✅ 生产环境 `TRADING_ENV=production` → 本地直连 |
| QMT 云端 RPC 桥接 | `utils/execution/remote_qmt_broker.py`（`RemoteQmtBroker`） | ✅ `QMT_RPC_URL` 配置时优先 |
| 模拟/影子 | `_build_simulated(cfg, shadow=True)` | ✅ 连接失败降级 + 告警 |
| 依赖声明 | `requirements-win.txt` §QMT/xtquant | ✅ 已声明（xtquant 非 PyPI，由 QMT 客户端分发） |

`broker_factory.get_broker()` 的既有降级链：sim → shadow → RemoteQmt（RPC）→ Qmt（本地直连），任一级失败降级 SimulatedBroker 并告警。**程序化下单通道已完备。**

## §2 为什么不引入 vnpy

| # | 理由 | 说明 |
|---|---|---|
| R1 | 价值主张已被覆盖 | vnpy 在本清单中的唯一理由（程序化下单替代 GUI）已被 QMT 实现，且 QMT 对 A股/两融/ETF 的适配优于以期货 CTP 为主场景的 vnpy |
| R2 | 冗余通道违反不变量 | 双券商通道 = 双份对接面、双份风控审计面、双份故障域，直接冲击 **I-09**（任何交易必须存在可追溯 source→signal→decision→order→fill 链）的单一可追溯性 |
| R3 | 与切换窗风险不匹配 | 生产切换窗 = 2027-01-02~01-09（R-3）。在切换窗前后引入新执行栈，与「任何模型切换必须可 rollback」（I-06）所要求的回滚简洁性直接冲突 |
| R4 | 新增强依赖面 | vnpy 需独立 EventEngine/MainEngine 进程模型 + 穿透式认证 + 新网关配置，属重型框架引入，与 09-02 决策 2「2027 前不引入新框架」的精神相悖 |
| R5 | 真实缺口不在此 | 当前执行链路的未完成项是 **W7.2.1 T15「QMT paper 验证」**（ROADMAP §历史里程碑未竟项），属**验证未做**而非**通道缺失**。引入 vnpy 不解决该问题，反而稀释注意力 |

## §3 真正的缺口与替代动作

| 缺口 | 性质 | 建议动作 | 时点 |
|---|---|---|---|
| W7.2.1 T15 QMT paper 验证未完成 | **验证缺口**（非能力缺口） | 完成 QMT paper trading 全链路验证并出报告 | 冻结窗前（09-19 前）或随 01-02~01-09 切换窗前置 |
| `xtquant` 未安装导致工业级检查 WARN | 物理阻塞（ROADMAP L49 记为 C1） | 在实盘机安装 QMT 客户端并配置 `qmt_path` | 同上 |
| `broker_adapters.py` 中 GUI 注释 | **部分为死代码** | `from pywinauto import Application` 是注释；但 `ThsBrokerAdapter(mode="gui")` **分支是真实代码且有测试覆盖**（`tests/unit/test_g7_broker_adapters_boost.py` 8+ 处断言）。**只能注释级标注，不可删除分支** | 已于 09-05 完成标注（零行为变更） |
| `ThsBrokerAdapter` live 模式 stub 返回成功 | **潜在 P0 风险（已知未加固）** | 两种模式的 `_do_submit_order()` 均只打 "TODO: 实际接入" 日志后置 `SUBMITTED` 并返回 True，未向券商发出请求。若 `USE_LIVE_BROKER_ADAPTERS` 开启 + `live: true`，会把未真实提交的单据记为已提交（污染 FillsStore/PnL）。**建议改为 fail-closed（REJECTED + False）对齐 I-04**，但需独立评审并同步改 8+ 处测试断言 | **待你决定**（属行为变更，不在本次"清理"范围内） |
| GUI 依赖仍在 `requirements.txt` / `-win.txt` | 依赖噪声 | 已加注记：全仓零引用、仅注释提及、保留声明的原因与移除条件（未删除条目，避免误伤未实现分支的可追溯性） | ✅ 09-05 完成 |

## §4 重启条件（保留可证伪性）

若未来出现下列任一情形，本文结论应被重新评估：

1. QMT 通道被证实无法满足业务需求（如：券商不支持 MiniQMT、需要期货/期权 CTP 直连、需要跨市场统一网关）；
2. `broker_factory` 的 QMT 适配被判定为长期不可维护；
3. 业务扩展到 QMT 不支持的品种（商品期货、境外市场）。

届时仍需独立走 spec→design→task→实现→验证，且准入前置检查表 `pushed_at` 距今 ≤12 个月。
