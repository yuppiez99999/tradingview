# 测试金字塔实施方案 — 断根"每次都有 bug"

## Context（为什么做这件事）

最近 3 轮审计（v8.6.4 → v8.6.7）每轮都发现新 bug，共修复 11 个（3 P0 + 8 P1）。**根因不是审计不够仔细，而是已修复的 5 条关键链路没有回归测试保护**：

- P1-G 修复了 `phase_hedge_fund` 的 `ks = KillSwitch()` 未注册 callback，但**遗漏了** `phase_signal` 中同样的 bug（BUG#5），3 周后才被发现
- BUG#1 修复了 `overnight_gap_monitor` 的 `FAIL_CLOSED_PCT=-0.04` 误触发 L3，但**同类问题**在 `market_circuit_breaker` 中也存在（BUG#1b），同一轮才发现
- 每次修复后只能靠"再来一轮审计"验证，无法防止回归

**本方案目标**：对 5 条关键链路建立三层测试金字塔，让每个已修复的 bug 都有对应的回归测试，**从被动审计转向主动防御**。

### 核心设计原则

1. **回归优先**：每个已修复 bug 必须有对应回归测试，函数名含 bug 编号（如 `test_p0d_none_fields_fallback_to_positions_estimation`）
2. **Mock 边界清晰**：
   - 单元层：全 mock（astock/akshare/broker/文件系统）
   - 集成层：仅 mock 外部数据源，保留模块间真实调用
   - E2E 层：使用真实历史报告，仅 mock 实时数据源
3. **不破坏现有**：现有 19 个测试文件保留不动
4. **黄金数据**：E2E 使用 `daily_pnl_report_2026-07-21.json`（26 标的真实生产报告）
5. **自定义标记**：`@pytest.mark.p0` / `@pytest.mark.p1` / `@pytest.mark.bug('P0-E')` / `@pytest.mark.unit` / `@pytest.mark.e2e`

### pytest 配置（新建 pytest.ini）

```ini
[pytest]
testpaths = tests tests/unit tests/integration tests/e2e
python_files = test_*.py verify_*.py
markers =
    unit: 单元测试 (全 mock, <1s)
    integration: 集成测试
    e2e: 端到端测试 (真实历史数据)
    regression: 回归测试
    p0: P0 致命级 bug 回归
    p1: P1 风险缺口级 bug 回归
    bug(id): 关联 bug 编号
addopts = --strict-markers --strict-config -ra --tb=short
```

## 设计决策

1. **不直接迁移 verify_*.py**：verify 脚本是 print+assert 风格，无 fixture 复用，重复严重。新建 pytest 测试文件，但保留 verify 脚本作紧急工具。
2. **三层目录而非扁平**：不同层 Mock 策略不同，conftest 隔离避免污染；`pytest -m unit` 比 `pytest tests/test_*_unit.py` 优雅；CI 可分层跑。
3. **`_extract_positions` 单独成文件**：报告兼容是独立关注点，集中便于追溯 BUG#2/#3。
4. **E2E 黄金数据选 2026-07-21**：真实生产报告，26 标的，有真实 L2 触发记录（80.36% margin）。
5. **用 pytest.ini 而非 pyproject.toml**：项目无 pyproject.toml，pytest.ini 是最简方案。
