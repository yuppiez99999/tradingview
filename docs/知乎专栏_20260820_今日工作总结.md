## 四、可观测性闭环：structlog + pydantic Schema + pytest-benchmark + OpenTelemetry

可观测性是 Phase B 的核心交付——"看不见的系统不可信"。今日把结构化日志、事件 Schema、性能基准、分布式追踪四件套全部落地。

### 4.1 结构化日志（structlog）

`utils/observability/structured_logger.py`：StructuredLogger 升级为 structlog JSON 后端 + 标准 logging 回退 + `bind()` 上下文绑定。

设计要点：structlog 不可用时优雅降级到标准 logging，保证环境依赖不硬阻断。

### 4.2 事件 Schema（pydantic v2）

`utils/observability/event_schema.py`：

| Schema | 字段 |
|--------|------|
| `OrderEvent` | order_id / symbol / side / qty / price / filled_qty |
| `RiskEvent` | risk_level / trigger / action |
| `ExecutionEvent` | phase / duration_ms |
| `PipelineEvent` | pipeline_name / step / step_index |

pydantic v2 校验保证事件结构契约，下游消费方无需防御性编程。

### 6.2 三点启示

**启示一：渐进启用比一次性开关安全得多。** Phase B 的四个 flag（drift_detector / feedback_loop / auto_retrain / orchestrator）不是一次性全开，而是状态机逐级推进——每级稳定 3 天才 advance 到下一级。B1 今日启用的是"只读监控"（drift_detector 启用但仅告警不干预），这是渐进启用的安全起点：先观察漂移是否发生，再决定是否动手修正。21 天观察期 + 3 天稳定门槛 + 4 级状态机 = 33 天从"观察"到"全自动闭环"的安全路径。**渐进的本质是把"一次性大爆炸"拆成"多次小验证"**。

**启示二：门禁不是"卡你"，是"替你守住底线"。** v8.7 设三门禁（D9 覆盖率 / D10 超大文件 / D11 shadow 稳定），今日 D9 达标但 D10/D11 未达标——这正是门禁的价值。D10 拦住了两个 2600+ 行的超大文件进发布，D11 拦住了 shadow 只跑 0 天的系统进发布。门禁当前判定 [BLOCK]，退出码 2 阻断合并——这不是"卡进度"，是"替你守住 v8.7 的发布质量契约"。**门禁的设计目标是"让不达标的状态无法意外发布"**，而非"让所有状态都达标"。

**启示三：可观测性是"看不见的系统不可信"的工程落地。** 今日把 structlog（结构化日志）+ pydantic Schema（事件契约）+ pytest-benchmark（性能基准）+ OpenTelemetry（分布式追踪）四件套全部落地。KillSwitch 风控检查 2327 Kops/s 意味着单次检查 ~0.43 μs——这个数字不是"跑个 benchmark 看看"，而是"盘中实时风控延迟要求是否满足"的工程证据。可观测性的三层数据：日志（事后排查）+ 指标（性能基线）+ 追踪（链路定位），缺一不可。**没有可观测性的系统是黑箱，黑箱在出事时只能"猜"**。
