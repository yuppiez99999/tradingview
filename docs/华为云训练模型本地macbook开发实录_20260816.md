# MacBook Pro 本地开发 + 华为云 ModelArts 训练：首次对接的工程实录与踩坑分析

> 本文记录将 A 股多因子选股系统的 LightGBM 增强训练任务从 MacBook Pro（M5 Max）迁移至华为云 ModelArts 公共资源池的完整工程过程。教程预估 3 小时，实际耗时 10 小时。文章聚焦链路搭建中的非平凡故障点及其工程解法，供同路线开发者参考。

## 一、问题背景与架构选型

### 1.1 本地瓶颈

目标系统为 A 股量化交易研究框架，核心训练任务为基于 Qlib 的 LightGBM 多因子模型训练。本地开发机为 MacBook Pro M5 Max（ARM64 架构，16GB 统一内存）。在以下场景中本地算力不足：

- 训练数据覆盖 CSI300 全成分股 × 2015–2026 年日频特征（Alpha158 特征集），单次全量训练内存峰值约 12GB
- 增强训练需进行时序交叉验证（TSCV）多轮迭代，单轮约 25 分钟，串行 5 轮阻塞交互式开发
- 模型搜索（AutoLearn）需并行评估数十组超参，本地并发受限于物理核数

### 1.2 架构决策

采用**本地编辑—云端训练—本地评估**的分离架构：

| 层 | 承载 | 职责 |
|---|---|---|
| 开发层 | MacBook Pro | 代码编写、特征工程调试、小样本（<5%）逻辑验证 |
| 训练层 | 华为云 ModelArts 公共池 | 全量数据训练、超参搜索、模型产出 |
| 存储层 | 华为云 OBS | 训练数据、模型 artifact、日志持久化 |
| 镜像层 | 华为云 SWR | 训练环境容器化镜像仓库 |

该架构的核心约束：**Mac 为 ARM64，ModelArts 公共池为 x86_64**。这一架构差异是后续构建阶段主要故障的根因。

## 二、10 小时耗时归因分析

教程基于理想路径给出 3 小时预估。实际耗时分布如下：

| 阶段 | 教程预估 | 实际耗时 | 故障密度 | 主要根因 |
|---|---|---|---|---|
| 账号 + IAM + AK/SK | 35 min | 60 min | 中 | 实名认证人脸识别重试、SK 单次显示未及时持久化 |
| CLI 安装 + OBS 桶创建 | 20 min | 90 min | 高 | Homebrew 安装失败、`hcloud` 未加入 `PATH` |
| 数据上传至 OBS | 20 min | 60 min | 中 | `obsutil` endpoint 拼写错误、家宽上行带宽限制 |
| Docker 镜像构建 | 30 min | 150 min | **极高** | ARM→x86 跨架构构建、`.dockerignore` 缺失致镜像膨胀 |
| 镜像推送 + ModelArts 开通 | 25 min | 60 min | 中 | SWR 临时登录指令过期、新账号余额不足 |
| 训练作业提交 | 30 min | 120 min | 高 | OBS 挂载路径与容器内路径不一致、`qlib.init` 数据完整性校验失败 |
| 模型回拉 + 本地验证 | 10 min | 60 min | 低 | pickle 反序列化路径不匹配 |

**关键观察**：纯执行时间约 3 小时，排障时间约 7 小时。故障呈"每步偏差 5%–10%、链路串联后指数放大"特征，这是分布式系统首次对接的典型成本结构。

## 三、工程链路

完整链路 13 步，可抽象为三个阶段：

```
┌─────────────────────────────────────────────────────────────┐
│  阶段 A：凭证与基础设施（步 1–4）                              │
│  IAM 子账号 → AK/SK → hcloud CLI → OBS 桶（data/models）      │
└─────────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────────┐
│  阶段 B：环境构建与分发（步 5–8）                              │
│  数据 → OBS  │  Dockerfile → 镜像（ARM→x86）→ SWR 推送         │
└─────────────────────────────────────────────────────────────┘
                          │
┌─────────────────────────────────────────────────────────────┐
│  阶段 C：训练与回流（步 9–13）                                 │
│  ModelArts 作业（镜像+数据挂载+规格）→ 日志 → 模型 → Mac 验证   │
└─────────────────────────────────────────────────────────────┘
```

设计原则三条：
1. **代码与数据传输通道分离**：代码走 Docker 镜像（SWR），数据走对象存储（OBS），避免单一通道拥塞
2. **本地仅验证逻辑，云端仅执行规模**：小样本（1%）本地跑通后再全量上云
3. **一切 artifact 落 OBS**：日志、checkpoint、模型均持久化至 OBS，不依赖容器临时文件系统

## 四、关键故障点与技术分析

### 4.1 AK/SK 持久化失败

**现象**：IAM 创建子账号 `qt-admin` 时，AK/SK 仅在创建瞬间返回一次，关闭对话框后 SK 不可再获取。

**根因**：华为云 IAM 访问密钥设计为单次明文返回，后续仅保留密钥指纹用于比对，这是安全设计的合理约束，但文档未充分强调。

**工程解法**：创建瞬间立即写入 macOS Keychain（`security add-generic-password`），后续所有 CLI 调用通过命令替换现取现用，密钥不落明文文件：

```bash
# 持久化（一次性）
security add-generic-password -a $USER -s huaweicloud_ak -w "$AK"
security add-generic-password -a $USER -s huaweicloud_sk -w "$SK"

# 调用（每次）
hcloud configure set \
  --access-key=$(security find-generic-password -a $USER -s huaweicloud_ak -w) \
  --secret-key=$(security find-generic-password -a $USER -s huaweicloud_sk -w) \
  --region=cn-east-3
```

**教训**：云凭证管理应纳入项目工程化范畴，Keychain 是 macOS 上最干净的方案，优于 `.env` 文件（易误提交 git）。

### 4.2 ARM64 → x86_64 跨架构镜像构建

**现象**：本地 `docker build` 产出的镜像推送至 SWR 后，ModelArts 训练作业启动即失败，日志报 `exec format error`。加 `--platform linux/amd64` 后构建卡在 `uv sync` 阶段 20 分钟无输出，最终报 `platform linux/amd64 not supported`。

**根因分析**：
1. Mac M5 为 ARM64 架构，ModelArts 公共池计算节点为 x86_64，二者二进制不兼容
2. Docker Desktop 默认未启用 Rosetta 2 交叉编译加速，`--platform` 指令虽生效但走 QEMU 软模拟，性能极差且对某些系统调用不支持
3. `uv sync` 在软模拟下处理锁文件时触发未定义行为

**工程解法**（三件套，缺一不可）：

```bash
# 1. Docker Desktop → Settings → "Use Rosetta 2 for x86/amd64 emulation" → Apply
# 2. 预拉基础镜像（避免构建时网络阻塞）
docker pull --platform linux/amd64 python:3.11-slim

# 3. 显式平台指定构建
docker build --platform linux/amd64 \
  -t swr.cn-east-3.myhuaweicloud.com/qt/qt-qlib-trainer:latest \
  -f cloud/docker/Dockerfile.qlib-trainer .
```

**进一步优化**：若构建频繁，应在云上构建（SWR 支持触发器构建或 CCE + buildx），彻底回避本地跨架构问题。本教程阶段本地构建可接受，生产化应迁移构建路径。

### 4.3 `.dockerignore` 缺失致镜像膨胀

**现象**：首次构建产出镜像 8.2GB，推送 SWR 耗时 40 分钟未完成。

**根因**：未配置 `.dockerignore`，`COPY . .` 语义将本地 `data/`（730MB）、`models/`（历史模型 5GB+）、`.venv/`（虚拟环境 1.5GB）全部打入镜像上下文。

**工程解法**：项目根目录配置 `.dockerignore`：

```
data/  data_cache/  models/  logs/  reports/  output/
.venv/  __pycache__/  .pytest_cache/  .mypy_cache/  .ruff_cache/
game/  games/  *.ps1  cache/  .git/
```

配后镜像降至 1.5GB，推送 5 分钟完成。**此项优化在整条链路中收益最大，应在首次构建前完成。**

### 4.4 OBS 挂载路径与容器内路径不一致

**现象**：训练作业配置数据存储 `OBS: qt-data → /cache/data`，启动命令 `--data-dir /cache/data/qlib_data/cn_data`，作业启动即 `FileNotFoundError: /cache/data/qlib_data/cn_data`。

**根因**：OBS 桶内对象 key 层级与容器挂载点层级未对齐。上传时执行 `obsutil cp -r ~/QuantData/qlib_data/ obs://qt-data/qlib_data/`，挂载后容器内路径为 `/cache/data/qlib_data/`，但 `qlib.init` 期望的 `cn_data` 目录位于更深一层。

**工程解法**：路径映射必须满足等式：

```
OBS 桶内 key 前缀 + 挂载点 = 容器内期望路径
```

即上传目标应为 `obs://qt-data/qlib_data/cn_data/`（含 `calendars/`、`instruments/`、`features/` 三子目录），挂载点 `/cache/data`，则容器内 `/cache/data/qlib_data/cn_data/` 正确命中。

**通用化建议**：训练脚本中路径不应硬编码，应通过 `resolve_path()` 函数依据环境变量（`QT_PLATFORM`、`QLIB_DATA_DIR`）动态解析。这是跨环境（本地/云/CI）复用的前提。

### 4.5 `qlib.init failed` —— 数据完整性校验

**现象**：作业状态转"失败"，日志 `qlib.init failed`，无进一步堆栈。

**根因**：`obsutil cp -r` 上传时因网络抖动漏传 `features/` 子目录，`qlib.init` 校验目录结构失败但错误信息不 verbose。

**工程解法**：上传后强制校验，不盲提交作业：

```bash
obsutil ls obs://qt-data/qlib_data/cn_data/ -limit=20
# 必须确认输出包含 calendars/ instruments/ features/ 三目录
```

**进一步建议**：训练脚本入口增加数据完整性断言（`assert` 三目录存在且非空），fail-fast 并输出明确诊断，优于依赖 `qlib.init` 的隐式失败。

### 4.6 新账号余额门槛

**现象**：提交训练作业被拒，提示账户余额不足。

**根因**：ModelArts 公共池按量计费，但华为云对新账号设有最低余额门槛（约 ¥100），即使单次作业实际消费仅 ¥0.25 也需先充值。

**解法**：费用中心预充 ¥100。本教程实际消费 < ¥1，余额可长期复用。

## 五、可复现的训练作业配置

### 5.1 Dockerfile 关键片段

```dockerfile
FROM python:3.11-slim
RUN pip install --no-cache-dir uv
WORKDIR /app

COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev
RUN pip install pyqlib lightgbm

COPY ms_strategy/cloud_train/ ./ms_strategy/cloud_train/
COPY ms_strategy/training/    ./ms_strategy/training/
COPY qlib/  ./qlib/  COPY utils/ ./utils/
COPY config/ ./config/  COPY configs/ ./configs/
COPY lgb_trainer/ ./lgb_trainer/
COPY lgb_enhanced_trainer.py lgb_tscv_trainer.py autolearn_trainer.py ./

ENV QT_PLATFORM=cloud
ENV QLIB_DATA_DIR=/cache/data/qlib_data/cn_data
ENV QUANT_DATA_ROOT=/cache/data

CMD ["uv", "run", "python", "ms_strategy/cloud_train/modelscope_train.py"]
```

### 5.2 训练作业启动命令

```bash
uv run python ms_strategy/cloud_train/modelscope_train.py \
  --data-dir  /cache/data/qlib_data/cn_data \
  --market    csi300 \
  --start     2015-01-01 --end 2026-08-14 \
  --train-end 2024-12-31 --valid-end 2025-06-30 \
  --model     lightgbm \
  --num-leaves 128 --boost-round 500 \
  --learning-rate 0.02 --max-depth 8 \
  --output    /cache/output
```

资源规格：`modelarts.bm.8c32g.cpu`（8 vCPU / 32GB），公共资源池，单节点。CSI300 全量训练约 28 分钟，消费 ¥0.25。

## 七、工程化建议清单

以下为本次实践沉淀的可复用工程规范，按优先级排序：

1. **AK/SK 即时持久化至 Keychain**，禁止明文文件、禁止仅依赖浏览器会话
2. **`.dockerignore` 先于首次构建配置**，排除一切非运行时依赖
3. **跨架构构建显式声明 `--platform`**，并启用 Rosetta 2 加速；生产化应迁移构建至云端
4. **数据上传后强制 `obsutil ls` 校验目录结构**，训练入口增加完整性断言
5. **小样本（1%）先跑通全链路再扩量**，避免全量数据下排障
6. **路径解析走环境变量 + `resolve_path()`**，零硬编码，保证本地/云/CI 三环境复用
7. **日志、checkpoint、模型一律落 OBS**，容器临时目录视为不可信
8. **新账号预充 ¥100**，回避按量计费余额门槛
9. **长任务用 `nohup`/`tmux` 托管**，SSH 交互终端仅用于编辑与日志拉取

本次迁移总耗时 10 小时，其中纯执行 3 小时、排障 7 小时。故障分布符合"首次对接成本前置"的一般规律：链路中每步 5%–10% 的偏差，经 13 步串联后呈指数放大。

走通后的稳态成本极低：第二次相同链路预计 1 小时内完成，月度运维成本 < ¥5。本地 Mac 保持安静的开发体验，云端承担计算密集型任务，架构收益明确。

**核心经验**：首次对接的"过路费"不可避免，但应通过工程化手段（模板化 Dockerfile、路径解析函数、数据完整性断言、`.dockerignore`）将其转化为一次性投入，而非每次重复支付。本文列出的 9 条规范即为此目的沉淀，建议在项目初始化阶段即落实。
